## 1. 开跑前：两个服务器，缺一不可

开两个终端，各跑一条，**都不要关**：

```bash
# 终端 A —— 收数据的（8765）。脚本把字节 POST 到这里，落盘到 Data/flow/
python _tools/receive.py --port 8765 --dir D:/rblxTRGproject/Data

# 终端 B —— 给脚本的（8766）。执行器从这里取脚本本体
python -m http.server 8766 --bind 127.0.0.1 --directory _tools
```

**为什么要两个：** 8765 是**出**（数据从游戏里出来），8766 是**入**（脚本进游戏）。
端口不能混用，两个服务各占一个。

**不需要手敲：双击项目根目录的 `start_services.bat`。** 它把上面两条各起一个**独立窗口**
（各留各的日志，关一个不影响另一个），并把 `loadstring(...)` 那一行和热键直接印在横幅里。
两件它替你做掉的事：**先 `cd` 到项目根**（`--directory _tools` 是相对路径，不 `cd` 会伺服到别处），
**起之前先看端口**（第二次起的那个不会响亮地失败 —— 端口被占，它绑不上就死，
窗口一闪而过，**看起来和「服务已经在跑」一模一样**）。

**怎么确认活着：** 终端 A 每收到一段就会打一行 `RECV <名字> <字节数> <crc32>`。
没有这行 = 脚本没在发 = 采集没开始。

**为什么绕这一圈：** 直接把 1.4 MB 数据从 Studio 读回对话里要烧掉二十万 token。
让游戏自己 POST 到磁盘，字节就永远不经过对话。

## 3. 屏幕左上角那个面板怎么读

```
phase RUN  sample 1234  lines 5678
seg 90  buf 3210 B  fails 0
drop 0  spill 0  evt 1456
```

**`r60` 起是三行，不再是四行** —— `drv <状态> <裁决>  shut n/m start n/m` 那一整行
随驱动器一起删掉了（`DECISIONS_2` 202）。它原来报的「驱动器在哪一步、试到第几个关机候选」
现在没有任何意义，因为**按东西的只有你**。

| 字段 | 意思 |
|---|---|
| `phase` | `PRE` 还没确认流程 / `RUN` 运行中 / `DOWN/UP` 已确认关机、等重启 / `UP` 已重启、正在录重启后的稳定段 |
| `sample` | 第几次采样（每秒 4 次，上限 14400 ≈ 1 小时） |
| `lines` | 已经写进文件的文本行数 |
| `seg` | 已经发出去的 HTTP 段数（每段最多 48 KB） |
| `buf` | 缓冲区里还没发出去的字节 |
| `fails` | **连续**发送失败次数。到 12 就转存磁盘 |
| `drop` | 因为缓冲区满了被丢掉的字节。**这个不是 0 就要当回事** |
| `spill` | 因为发不出去而转存到磁盘的字节 |
| `evt` | 事件计数 |

### 3.1 核心闸：开机之前不写反应堆读数（`r60` 起）

**面板上**没有**的一个数，是「核心开了没有」** —— 它不在 `phase` 里，因为它是**另一件事**：
`phase` 说的是「流程走到哪」，而核心闸说的是「反应堆读数开始写了吗」。
闸打开时文件里会出现一条 **`COREGATE`** 事件（见 §4）。想从面板上看，看 `lines` 会不会跳：
闸开之前 `s.Core.*` 一个都不写，所以开机那一拍 `lines` 会明显往上跳一下。

**为什么要有它：** 冷态开局的时候，`s.Core.*` 那一堆读数全是**没意义的零**，
而它们是**最贵的一类行** —— 每一拍写一次、每拍都在变（因为从 0 开始爬），
把它们录进去等于用一场真班次去记「反应堆关机的时候，反应堆是关着的」。

**判据是游戏自己的旗标 `s.GameActive`，不是温度。** 用温度当判据会在
「开了但还没热」和「关了但还很热」两个区间上错 —— 而这两个区间**正好就是开机和关机**，
也就是你最想看清的两段。`s.GameActive` 是游戏自己说「核心彻底开好了」的那一句。

**它是锁存（latch），不是每拍问一次。** 一旦开过就永远开着，
因为**关机之后那些读数还要用** —— §3.3 的低温跳闸那条臂读的正是 `m.temp`。
一个每拍重新判的闸，会在关机的那一拍把温度读数掐掉，于是**永远检测不到低温跳闸**。

**它是「扣住」，不是「过滤」。** 闸关着的时候那个键**根本不进 `last` 表**，
所以闸一开，第一拍的值是**新键**、会被写下去。
如果实现成「照常记，只是不输出」，那么闸开的那一拍**正好等于**开机前的值时
（开机就是从常温开始的），那条读数会被判成「没变化」而**永远不出现** ——
两种实现在那之前逐字节相同，只在那一拍分岔。

**闸故意不管的两块：** 通用读数走查（`t.*`）和设施面板。
**开机流程本身就在那里面** —— 把它们也闸掉，等于把要录的东西挡在门外。

### 3.2 没有 DRIVER 了（2026-09-30 起，`r60`）

采集器**不按任何东西**。它只做两件事：**录**，和**封存**。

> **为什么删。** 你 2026-09-30 的原话：「注入后立刻开始（注意在核心完全开启前不要采集
> 温度、压力等），并且**不需要什么driver，只需要seal**：SEAL的情况是 1：手动关机，
> 2：核心自动关机如熔毁，温度过低等」。
> 驱动器的整个存在理由是「**替**你按那两个开关」，而这个理由**从来没有成立过** ——
> 删它之前的配置（`DrivePressControls = false`）它本来就一个都不按。
> 一台从不按东西的驱动器是一台**只生产状态名词的机器**，而那些名词
> （`arming` / `holding` / `press_shut` / `watching` / `shut_down` …）
> 每一个都要你花一次**真班次**才能出现一次，**它们本身不是你要的数据**。

**随之一起走的：**

| 删掉的东西 | 为什么它只能跟着走 |
|---|---|
| 屏幕上的 `DRIVER: ON/OFF` 按钮 | 没有驱动器可以开关 |
| `[rec] DRIVER: ...` 那两行控制台输出 | 同上 |
| `disarmed-by-user` / `rearmed` 两个阶段名 | 它们只描述那个按钮 |
| `DrivePressControls` / `ShutdownEndsShift` 两个「备用配置」 | 备用配置的**唯一**读者就是驱动器的按压逻辑 |
| `ShutdownEndsShift` / `pollDt` 两个量 | 各只有一个读者，都在 `driveStep` 里 |

**现在屏幕上只有一个按钮：`SEAL NOW`（红）**，热键 `RightShift` 也是它。
**任何时候按都安全** —— 它立刻写收据然后停止。

> **那段代码没消失，是归档了。** `_tools/_attic/driver/` 里三个文件
> （builder / selftest / 生成的 harness）完好无损 —— §1.4 第 2 条
> 「不要在没有替代品的情况下删除功能」。驱动器里那几个场景
> （这个游戏的两个开关长什么样、按下去有没有反应）**是关于这个游戏的测量**；
> 哪天要把它接回来，那是全部家底。删掉的只是它**挂在采集器上**这件事。

### 3.3 关机是怎么被认出来的（这半个活着）

它**从来不属于驱动器**，而是 `endReason()` —— 同一个函数**同时管**「自动封存」和
「收据上写什么死因」。四个信号，**任何一个第一次出现就认账**：

| 先看到的信号 | 收据 / 事件里写的理由 |
|---|---|
| `s.GameActive` 由 `true` 变 `false` | `shift over (GameActive true to false)` |
| `s.GameFail` 由 `false` 变 `true` | `shift failed (GameFail false to true)` |
| `s.MainframeMeltdown` 由 `false` 变 `true` | `machine room meltdown (MainframeMeltdown false to true)` |
| `m.temp` 连续 `SealColdSamples` 拍低于 `Config.LowTripF` | `cold trip (under 1000 F for N polls)` |

外加**只有温度**能触发的另一条：`m.temp` **连续** `SealHotSamples` 拍高过
`Config.MeltdownF` = 堆芯熔毁。它读的是**温度**，不是 `s.MainframeMeltdown` ——
那个旗标是**机房**的，§8.2 就是那一课（一次误记把机房熔毁写成了 39000 度的堆芯熔毁）。
**「连续 N 拍」是在说：一次读数不是判决。** 这个圈套买的是「别把一次坏读数写成死因」。

> **`everRan` 门（`r57`）**：冷态开局的一趟里堆芯从来没热过 —— 那时候「温度低」
> 不叫跳闸，叫**还没开机**。所以后面那几条全挂在 `everRan` 下面。
> 这个门和 §3.1 那道核心闸是**两件不同的事**：核心闸管「别录冷读数」，
> `everRan` 管「别把从没开过机的堆芯判成跳闸」。

> **旧笔记里的 `user-shut` / `shut-confirmed` / `watching` / `unsupported`
> / `off-waiting-arm` / `no-temp-readout` / `flow-complete` 全部作废** ——
> 它们是驱动器的裁决，`r60` 里一个字节都不剩。想知道某个名字还在不在，
> 用 `grep -c '<名字>' _tools/TRG_original_recorder.luau`，**不要相信回忆**。

## 4. 操作流程（你该按什么，按顺序）

### 4.0 先记住这条 —— 它决定了整个流程

> **关机 = 班次结束。** 不管是因为拉杆、低温跳闸、还是熔毁，只要堆芯关了，
> 班次就结束、**不能继续**（你的 Q3 + Q4）。

**而新班次开局，堆芯是冷的（你的 A1）。** 所以：

- 「开机」不是上一场结束之后的事 —— **它就是这个班次的开头**。
- 「关机」是这个班次的结尾。

**两半在同一个班次里，所以一次注入、一份文件就够：**

```
注入（此时堆芯冷）          ← 立刻开始录，但反应堆读数还扣着（§3.1 核心闸）
  → 你手动开机              ← 开机流程本身照录（t.* / 面板 / 事件都在）
  → 核心彻底开好            ← 游戏自己的 s.GameActive 翻真 → 核心闸打开
  → 你自己按下关机拉杆       ← 中间想录多久录多久，没有任何东西在计时
  → 班次结束  →  文件自动封存 ✓
```

**上一版这里是错的。** 它写的是「关机 = 班次结束 = 会话终止，所以一次注入永远录不到
两半，必须注入两次」—— 那个结论默认「开机」只能发生在**上一场结束之后**，
于是只能落进下一次注入。A1 把那个默认推翻了，**「两次注入」连同 D1 一起作废。**

**仍然成立的那一半：关机之后不能继续。** 所以关机之后**不再重新开机** ——
那个动作会**在一场戏里花掉你唯一的那次开关**，而且发生在客户端被杀前几秒。

## 5. 温度模型（**重要**）

**堆芯是两头跳闸的：太高会关机，太低也会关机。**

| 阈值（华氏 °F） | 是什么 | 记录器怎么用 |
|---|---|---|
| **1000** | **低温跳闸线** —— 低于它堆芯自动关机（你的 P7，2026-09-27 定的；原来写的是 2000） | 封存判定的**兜底之一**，**且要求先看到堆芯运行过**（见下） |
| **5600** | 游戏自己的状态边界 | **RUN / DOWN 的分界线**（比 1000 早，是「正在掉下去」的信号） |
| 17500 | 游戏自己的状态边界 | 只记录，不驱动 |
| 29500 | 游戏自己的状态边界 | 只记录，不驱动 |
| **39000** | **熔毁线** —— 高于它熔毁（你的 A2：**熔毁条件只有这一条**） | **熔毁判定 + 封存触发** |

> **1000 改的是这一份脚本的封存线，不改游戏。** 而且它**没有**修你 12:32 那趟：
> 那趟 `m.temp` 最低只到 **4316 F**，离 2000 和 1000 都差 2300 度以上，
> 冷跳闸那条臂**一次都没到过** —— 结束它的是 `SealDownSamples = 40` 那条兜底
> （收据原文 `SEAL held down 40 polls with no end signal`）。**两件事，别混**
> （取舍 `DECISIONS_2` 182）。`Config.LowTripF` 上面的注释写的是这个测量，不是新数字。

**两条线分工不同，别混：**
- 温度**高于** 5600 → 「核心在运行」
- 温度**低于** 5600 → 「核心正在掉下去」（**这是趋势，不是结论**）
- 温度**低于 1000** → **低温跳闸 → 关机 → 班次结束**（**这是结论**）
- 温度**高于 39000** → **熔毁 → 关机 → 班次结束**（**这是结论**，A2 说这是唯一的熔毁条件）
- 连续 3 次采样都低于 5600 → 才翻 `PHASE2 DOWN`（防抖）

> ⚠️ **「跳闸」和「熔毁」都要求「先看到堆芯跑起来过」。** 因为 A1 说**新班次开局
> 堆芯是冷的** —— 冷堆按定义就在 1000 以下。纯看数值（level）的判定会在你注入后
> **2 秒就把文件封掉**，里面什么都没有。所以温度那两条**必须先看到温度上过 5600**
> 才允许触发；旗标类（班次结束 / 班次失败 / 熔毁）一律**按变化**（edge）读，不按数值读。
>
> 这一条是本轮最重要的正确性决定，而且**有测试盯着**
> （`_tools/build_end_test.py` 的 E2，用 `_tools/selftest_end_test.py` 证明过它会红）。

> **低温跳闸 = 关机 = 班次结束。** 见 §4.0。
> 核心在跑的时候**别让它自己凉下去** —— 你一让它掉破 1000，
> 班次就结束了，而且**不是**以你要的那种方式。

**实测数字（2026-09-26 那次）：**

```
按下 SHUT        t=326.71   tempF=9377
（旧版这里写着「关机被接受 t=335.37，8.7 秒 / -431 °F」—— 假的，见 §8.1）
温度开始回升     t=404      tempF=10713
                 t=431      tempF=11838   ← 按下之后是升的
熔毁旗标亮       t=719.86                 ← 此时监视器读数 ~13000，不是 39000
第一次跌破 5600  t=735.23   tempF=4785
翻 DOWN          t=735.82
跌破 2000        t≈739.7    （推算，两次采样之间）
班次结束         t=740.33                 ← 按下之后 414 秒
```

> **上面那行 `跌破 2000` 没有跟着改成 1000，因为它不是阈值而是那次观测的重建。**
> 它是**按旧线 2000 推算**出来的（两次采样之间），而且如果游戏真正的线是 1000，
> 那么「跌破 1000」应该**晚于** `班次结束 t=740.33` —— 也就是说那次结束**不是**低温跳闸干的。
> 两条路都没有足够的采样去定，所以**留原样 + 这一行注**，等下一次真跑重算。

**「按下关机 → 游戏宣告班次结束」= 414 秒 ≈ 6 分 54 秒。**

> ⚠️ **这一段原来是错的，而且错得很有教育意义。** 旧版写的是
> 「按下关机 → 堆芯到冷态 = 408 秒」，并由此推出「你必须早按关机」。
>
> **两个都不成立：**
> - 「到冷态」那 408 秒量的是**游戏拖了多久才结束班次**，不是停堆要多久。
>   堆芯从头到尾**没进过冷态**，而且**也不需要** —— 按下拉杆就是立刻关机。
> - 那个「早按」的结论**是从一个假的因果链上长出来的**（§8.1–§8.3）。

> 游戏什么时候宣布班次结束。

## 6. 数据在哪 / 什么时候算成功

**位置：** `D:\rblxTRGproject\Data\flow\original_<年月日>-<时分秒>`
（文件名前缀是 `Config.NamePrefix = 'flow/original_'`）

**成功 = 文件最后一行是 `## RECEIPT`。** 没有这行就是**没封存**，数据不完整。

```
## RECEIPT name=... samples=... lines=... events=... segments=...
   postfails=... spilled=... dropped=... flow=true/false
   drive=<状态>/<裁决> readouts=... hash=xxxxxxxx over=... kinds ...
```

- `flow=true` —— 记录期间**见过核心从运行状态掉下来**（`sawDown` 落地）。
  判据的线是 `CoreThresholds[1] = 5600 F` —— 游戏自己的 stallout 线（`INGAME_MANUAL` 87：
  「Stallout Possibility will occur if the core temperature is below ~ 6000F」），
  **不是** 1000 F 那条低温跳闸（你的 P7），两件不同的事。
- **`flow=false` 读作「没见它掉下来过」，不是「数据丢了」，更不是「这一份里核心从没冷过」。**
  `sawDown` 要先 `flowArmed`，而 `flowArmed` 要 `isRunning`（`tempF >= 5600`，也就是
  `m.temp` 有读数）连续 `DebounceSamples = 3` 拍 —— **核心还没开起来的时候这个门根本不开**。
  所以**冷启动的一趟在结构上永远给不出 `flow=true`**。`2026-09-26 23:00` 那一份核心冷了
  88 秒（`B 1 t=1.34` 三个 `s.Core.*` 全是 0，`EVT2072–2078 CLICK StartUpLever` 就是开机），
  `flow` 照样是 `false`。
  **冷启动的证据在 `s.Core.TemperatureVal`，不在收据这个字段里。** 见下。

### 温度要看哪一列（2026-09-26 加，Phase 49 量出来的）

**两条序列是互补的，各自只覆盖一半，而且它们接得上：**

| 序列 | 覆盖 | 性质 |
|---|---|---|
| `s.Core.TemperatureVal` | t≈0 → **t=97.90**（0 → 9420 F，≈98 F/s），之后**冻在 9420 不动** | 游戏自己的**状态** |
| `m.temp` | **t=98.77** → 结束 | 监视器上的**标签**，监视器没开机时读 `ERR F` |

接缝处的证据：`s.Core` 最后一拍 t=97.90 是 **9420**，`m.temp` 第一拍 t=98.77 是 **9330**
—— 90 F / 0.87 s = **103 F/s**，和那 98 F/s 同速。**两边对得上，所以两段都可信。**

**`m.fluct` 就是那一 tick 的温度增量**（391/393 行满足
`temp(下一拍) − temp(这一拍) == m.fluct`，逐字节相等）：
`temp` 是 `fluct` 的累加。**tick ≈ 1.8 s**（间隔中位数 1.79、众数 2.0），
`m.temp`/`m.press`/`m.fluct` 三个标签同一步一起变。
**别拿「每采一次」当时间步去算导数** —— 那是在拟合重绘时刻表。

**这一趟量出来的增益（F/tick，1 档冷却、只在 cblPct=75 那条带里可信）：**
`ΣcblPct` **+5.05/%**、每台冷却泵 **−58**、每个风扇 **−33**，当前温度项 **≈ 0**
（也就是**温度不回正，是个积分器**）。**别外推**：冷启动那段 CBL 输出 300%，
实测只有 +180 F/tick，线性模型给 +1104 —— **差 6 倍，这个关系是饱和的。**
噪声 sd ≈ 145 F/tick，**lag-1 自相关 0.655**（不是白噪声）。详见 `PROGRESS.md` Phase 49。
- ~~`drive=<状态>/<裁决>`~~ —— **`r60` 起没有了。** 驱动器整个删掉了，
  收据里不再有「它停在哪一步」。**收据里回答「谁结束的这一趟」的是 `SEAL <理由>` 那条事件**：
  理由的措辞**就是**死因本身（§3.3 那四条）。

**你会看到的事件（一次正常的跑完，种类就这几种）：**

```
EVT1 COREGATE Stats.GameActive went true; the core is fully on and the reactor readings start from this poll
EVT2 CLICK StartUpLever                    ← 你按开机拉杆那一拍（你按的每一次都在这）
EVT3 CLOCK the clock passed 12:00PM: the shift has started
PHASE1 RUN armed
...
EVT9 CLICK ShutdownLever                   ← 你按关机拉杆
EVT10 SEAL shift over (GameActive true to false)   ← 四条件之一：同一拍封存
```

> **`COREGATE` 是开机那一拍的锚。** 在它**之前**文件里也有行（`t.*`、设施面板、
> `CLICK`、`PHASE`）—— **只是没有反应堆读数**。所以「开机到底做了什么」要去
> `COREGATE` **之前**那一段找，而不是从 `s.Core.*` 的第一行开始读。
>
> **`CLICK` 是你按的每一次**（`ClickDetector` 和 `ProximityPrompt` 都算，按路径命名）。
> 它**不属于驱动器** —— 那条 hook 从来不在 DRIVER 段里 —— 所以删驱动器
> **一条点击记录都没少**。这是删得下去的前提，不是巧合。
>
> **`PHASE` 只剩下 `PRE` / `RUN` / `DOWN/UP` / `UP` / `RECOVER`。**
> 其余的阶段名都是驱动器的，已经不在。`RECOVER` 是 `r57` 加的：
> **「停堆之后又起来」不算关机**，别把它读成 DOWN。

- `hash` + `over` —— 收据覆盖的字节数里的 djb2 哈希。**`hash` 只覆盖收据以上**
- `kinds` —— 各类事件计数，一眼看出缺了什么

**封存现在在这些情况发生（按判定顺序）：**

| 原因 | 触发 | 延迟 |
|---|---|---|
| `shift over (GameActive true to false)` | 班次结束的直接信号 | **零延迟**，就在看到它的那一拍 |
| `shift failed (GameFail false to true)` | 班次判失败 | 零延迟 |
| `machine room meltdown (MainframeMeltdown false to true)` | 熔毁旗标翻起 | 零延迟 |
| `cold trip (under 1000 F for 8 polls)` | 低温跳闸，**且堆芯运行过** | 2 秒 |
| `core meltdown (over 39000 F for 8 polls)` | 温度**真的**超过 39000（A2 的那一条） | 2 秒 |
| `core read as down for 40 polls with no end signal` | 核心下去了但一直没信号 | 10 秒 |
| `GameActive false for 40 polls` | 进来的时候班次就已经结束了 | 10 秒 |
| `flow complete` | **DOWN 之后又真的 UP 了**（有东西被点亮过），再录 24 拍收尾 | 6 秒 |
| `sample cap reached, down=...` | 采到 14400 次（≈1 小时） | — |
| `user seal` | 你按 `SEAL NOW` 或 `RightShift` | 立刻 |
| `startup failed: ...` | 脚本自己崩了 | — |

### ✅ 上一版那个「39000 对不上」的疑点 —— 已解决（D9）

> **上一版这里挂着一个没查清的疑点：** 熔毁旗标 `s.MainframeMeltdown` 在 t=719.86 翻，
> 而那一刻监视器只有 **~13000 °F**，可 A2 说熔毁的条件「就这一条：温度 > 39000」。
>
> **你给了答案：** `MainframeMeltdown 是机房熔毁又不是核心熔毁`。
> 所以那根本不是矛盾 —— **它们本来就是两件事**：
>
> | 原因字符串 | 说的是什么 | 证据 |
> |---|---|---|
> | `machine room meltdown (...)` | 机房熔毁，**旗标翻起就算** | t=719.86 旗标翻，温度 13000（不相干） |
> | `core meltdown (over 39000 F for 8 polls)` | **核心**熔毁，A2 的唯一条件 | 要真的读到 >39000，且连续 8 拍（2 秒） |
>
> **上一版那条规则把两件事写成了一件事**，于是把一次「机房熔毁」写成了一次
> 「39000 度的核心熔毁」——**那次核心熔毁根本没发生过**。
> 一份收据上写错原因是比不写原因更糟的事：它是读者不再自己复核时唯一会信的那一行。
>
> **顺带修好了一个更大的问题：** 拆分之后，`Config.MeltdownF`（39000）
> **终于有读者了**。在此之前它是配置里一个没人看的常数 ——
> 因为「核心熔毁」那条规则一直被机房的旗标顶着。两个方向现在各有一条臂：
> 冷端 `LowTripF`（**1000**，你 2026-09-27 的 P7 定的；改之前是 2000），
> 热端 `MeltdownF`（39000），**都带 8 拍的驻留**。

> **为什么两条臂都要驻留（8 拍 = 2 秒）：** 单次读数不能定案。
> 温度是会抖的，一拍 40000 就封存等于把一个毛刺当成了一次熔毁。
> 这跟冷端那条是同一个理由，测试里两条都钉了「少一拍不响」。

### ✅ 缺陷①（上次丢掉收据的那个）—— **已修**

**上次发生了什么：** 文件写到 t=740.33 戛然而止，**`## RECEIPT` 没写成**。
脚本**看到了** `s.GameActive=false`（就在最后一个样本上），
但**没有任何规则去看它**，而且它判定得排在很后面 —— 脚本死在它后面那个 `task.wait` 里。

**现在的做法：** 新加的 `endReason()` **在每轮循环体的第一件事**就判定，
`GameActive` 由 true 变 false **零延迟封存**。

**为什么是 2 秒而不是 5 秒：** 不是随手定的，是上次的实测逼出来的：

| 事件 | 时刻 |
|---|---|
| 温度跌破 2000 °F | t ≈ 739.7 |
| `GameActive` 变 false | t ≈ 740.33 |
| 客户端被杀 | t ≈ **740.33** |

> 第一行是**按当时的封存线 2000 推算**的（现在这条线是 1000，见 §5），
> 但下面的结论**不依赖它** —— 那条兜底来不及触发，靠的是 `GameActive` 与客户端死亡
> **同一拍**（740.33 / 740.33），和低温线是多少无关。

**「跌破之后再等 5 秒」= t ≈ 744.7，比客户端死亡晚 4.4 秒** ——
那条兜底在上一场**根本来不及触发**。所以 zero 延迟 + 2 秒。

> **别再把它「优化」成多个信号互相印证。** D4 的字面意思（「三条信号一起，
> 谁的窗口先到就谁封」）听起来像**要求信号一致**，而那种写法的自然实现是
> 「关机信号 **且** 先看到核心下来」。**变异测试里第三条就是这个 ——
> 它会让 E1 变红。封存宁可早，不可等。**

## 7. 文件格式速查

**只记变化。** 没变化的采样不占一行 —— 这是设计，不是丢数据。

| 行 | 格式 | 意思 |
|---|---|---|
| `B` | `B <sample> <t> <key=value ...>` | **基线**，开头把所有读数的初始值铺一遍 |
| `S` | `S <sample> t=<秒> dt=<毫秒> rd=<毫秒> <key=value ...>` | 有变化的那一次采样 |
| `EVT<n>` | `EVT<n> <种类> <内容>` | 事件 |
| `PHASE<n>` | `PHASE<n> <名字> t=<秒> ...` | 阶段翻页 |
| `## RECEIPT` | 见 §6 | 封存收据，**最后一行** |

**键的前缀：**

| 前缀 | 意思 |
|---|---|
| `m.` | 主监视器的读数（`m.temp` `m.press` `m.fluct`） |
| `c.` | **控制**状态（`c.cbl1On` `c.cbl1Lvl` `c.fanCount`） |
| `s.` | 系统/服务状态（`s.GameActive` `s.Core.RadiationVal`） |
| `z.` | 汇总（`z.systems` `z.parts`） |
| `r.` | 反应堆相关读数 |
| `t.` | 屏幕上的文字部件（`t.MainMonitorFrame.TempLabel`）。**同一个值往往在好几个监视器上各有一份**，所以会有 `t.` / `x.` 两组重复 |
| `x.` | 屏幕文字的别名路径 |
| `v.` | **屏幕 `Visible`**（`v.shutdown` `v.detonation` `v.boot` `v.error` `v.malfunction` `v.revive`）。**字写在隐藏 frame 上、靠翻 `Visible` 拿出来显示** —— 原版的关机/开机/熔毁提示全是这个形状。见 §11 ⑥ |
| `g.` | **玩家自己屏幕上**的对象旗标（`g.<路径>` = 那个对象**自己**的可见/启用），外加五个普查/异常计数 `g.objects` `g.over` `g.unreadable` `g.labels` `g.labelOver`。**Phase 55 加的，见下面那一节** |
| `log.panel` | 设施事件日志面板的**整块快照**（排序、无行号、一行） |
| `fc.panel` | 子空间预测面板快照 |
| `q.panel` | 配额进度面板快照 |

**`q.` 下面三个新键（B1 那条「怎么算开机了」）：**

| 键 | 是什么 | 什么时候写 |
|---|---|---|
| `q.timeText` | 配额监视器上时间那格**原本的字符串**（`TimeLabel.Text`） | 只要它变了就写 |
| `q.clock` | 从 `12:00PM` 起算的**分钟数**（正向走的 12 小时盘） | **只在字符串解析成功时**才写 |
| `q.up` | `q.clock > 0` —— 「开机了」 | 同上 |

> **`q.up` 在正 12:00 PM 那一分钟必然是 `false`。** 12 小时盘把正午放在 `0`，
> 而 `q.up` 是 `mins > 0` —— 所以整个表盘上**只有「12:00 PM」这一分钟**读 false，
> 其余 1439 分钟全是 true。这是判据的形状，不是噪声。但它**不能**用来判断
> 「正午附近是不是班次边界」：正午是 **Equinox 事件的起点**
> （`INGAME_MANUAL` 114/148 原文「12PM marks the beginning of the Equinox Event」），
> 班次是 6AM→6PM（`DECISIONS` 28），**正午在班次正中间**。

> **为什么要三个，而不是就写一个布尔值。**
> `q.up` 是**结论**，`q.clock` 是**结论的依据**，`q.timeText` 是**没被解读过的原始读数**。
> 如果记录器只写 `q.up`，将来发现判据错了（比如那个时钟不是 12 小时盘、
> 或者它到某一点会回绕），**这份文件就再也回不去了** —— 没人能从一个布尔值里
> 重建出原始字符串。三个都留着，判据就永远可以事后重算。
>
> **解析失败就一个都不写**，而不是写个 `false`：`false` 的意思是「读了、算出来没开机」，
> 和「没读懂」是两件事，混起来之后这一列就不可信了。
>
> **`CLOCK` 事件什么时候记：** 第一次读到时间时记一条（那是一句**状态**，
> 不是一次到达 —— 如果你注入的时候班次已经开了，它会如实这么写）。
> **之后分两种，取决于注入那一拍读到的是什么：**
> - 注入时读到**还没开机**（`q.up=false`）→ 第一次 `q.up` 变 true **就是班次开始**，
>   记 `the clock passed 12:00PM: the shift has started`，控制台也打一行；
> - 注入时读到**已经开机**（`q.up=true`）→ 盘已经越过正午了，它得**绕满一圈**才会
>   再读到「过了正午」，所以后面每一次跳变都是**表盘在走**，记
>   `the clock moved to <原文> -- the dial, not a shift boundary: the core was already up at inject`。
>
> **为什么必须分开，而且为什么这是修出来的。** `2026-09-26 23:00` 那份是**中途注入**的，
> 记录器当时在**班次正中间**连着记了
> `the clock is back at 12:00 PM` 和 `the clock passed 12:00PM: the shift has started`，
> 两句隔 60 秒，**两句都是假的** —— 那 60 秒里 `m.temp` 从 12865 走到 12979 F，
> 什么都没结束、什么都没开始。麻烦在于**第二句和真事长得一模一样，因为它就是真的那次越过**；
> 唯一能区分的是注入那一拍的状态，所以那个状态被留着
> （`clockStartedUp`，见 `_tools/build_clock_test.py`）。
>
> **修法只改措辞、不删读数。** 原文照样发，`q.clock` / `q.up` 照样由 `readQuota` 写，
> 所以那一刻仍然在文件里、仍然可以事后捞出来。**拒绝过度解读一个读数，
> 和把它丢掉不是一回事** —— 这一点上面「为什么要三个」那段早就料到了
> （原话：「或者它到某一点会回绕」），也正是因为原始字符串一直在，
> 这次回绕才能从文件里被认出来而不是被猜出来。

**事件种类：**

| 种类 | 意思 |
|---|---|
| `CLICK` | **本客户端看见的一次点击**（有标签，如 `Coolant1-OFF`） |
| `UNATTR` | **值变了但本客户端没看见点击** —— `UNATTR c.cbl1Lvl 2->1 (last click 41 polls ago)` |
| `TMAP` | 屏幕文字路径登记 |
| `TEXT` | 某块文字变了 |
| `ANIM` | 一个 label 在**一次采样内**变了太多次 → 判为动画，丢弃。**注意这句话目前有假**：一趟实测里 12 条全是 `moved 5 times`，而 `thisPoll` 每拍清零、正常永远到不了 5 —— 见 §11 ⑦ |
| `NOISY` | 变化太频繁 → 判为噪声，丢弃 |
| `GMAP` | **玩家 GUI 的一个键登记**（`g.` 出现在变化行里而在整份文件里找不到 `GMAP`，就是没人认领的布尔） |
| `GUI` | 玩家 GUI 的普查（`objects= over= unreadable= labels= label_over=`） |
| `PERF` | **采集器自己的成本**，每 `PerfPolls = 240` 拍一行（见下） |
| `COREGATE` | **核心闸打开的那一拍**（`s.GameActive` 由真变…… 就是它翻真）。**反应堆读数只在它之后写**，所以这一行是「开机段」和「运行段」的分界（§3.1） |
| `SAM` | **注入那一拍的 SAM 状态**（开着/关着），只记一笔，不带任何指令 |
| `CLOCK` | **配额时钟**越过 12:00PM（B1 的「开机了」）、第一次读到、或**表盘绕回正午** —— 中途注入时最后这种会写成 `the dial, not a shift boundary`，见上面 `q.` 那一节 |
| `STATADD` / `STATDEL` | 部件/模型增删 |
| `LAMPMAP` / `LAMPPAL` | 灯清单 / 灯调色板 |
| `READOUTS` | 读数普查结果 |
| `SEAL` | 封存 |
| `POLLERR` / `FATAL` | 出错（`DRIVEERR` 随驱动器一起删了 —— 它只报「驱动器这一拍抛错了」） |

### 7.1 玩家 GUI（`g.`，Phase 55 加的）

**为什么只能这个采集器干：** `PlayerGui` **只在拥有它的那个客户端里存在，什么都不复制**。
服务端看不见它，所以这一节的数据**只有注入客户端的那一趟**才有。

| 你看到的 | 意思 |
|---|---|
| `g.<路径>=true/false` | 那个对象**自己**的旗标。`GuiObject`（Frame / TextLabel / TextButton…）是 `Visible`，`LayerCollector`（ScreenGui / SurfaceGui / BillboardGui）是 `Enabled` |
| `g.objects` / `g.labels` | 这一拍记了多少个对象 / 多少个标签 |
| `g.over` / `g.labelOver` | **被上限砍掉的个数**（`MaxGuiObjects=600` / `MaxGuiLabels=400`）。**`g.over>0` 就说明记录不完整** —— 「600 个」和「至少 600 个」是两条结论 |
| `g.unreadable` | 两个旗标**都不答**、被丢掉的对象个数（不猜，只计数） |

**三条必须知道的：**

1. **`g.` 记的是对象自己的旗标，不是「玩家能不能看见」。** 一个 `Visible=true` 的标签如果
   被藏在 `Visible=false` 的 frame 底下，`g.` 仍然写 `true`。想还原有效可见性得自己沿血缘算 ——
   采集器**故意不每拍算**，因为那要对每个对象再读一遍祖先，是这一节最贵的一笔。测试里有一条
   （G10）专门钉住这个设计，**别把它「修好」**。
2. **标签的文字不在这里**，它在 `t.` / `x.`（走原有那套读数走查，连去抖和颤抖判决一起）。
   `g.` 只管旗标。**同一个字符串不会有第二个读者。**
3. **采集器自己的那块面板不会进记录**（按血缘排除，不按名字）。所以你在文件里
   **不会**看到左上角面板的读数 —— 那是故意的，不然它会把自己每拍改四次的文字录进来，
   还会被自己的噪声判决骂一句。

**`PERF` 行怎么读**（每 240 拍一行，全是 `os.clock` 量出来的）：

```
PERF polls=240 hz=1.66 read_ms=... pass_ms=... flush_ms=... wall_ms=... cpu_pct=... read_pct=... worst_ms=...
```

| 字段 | 意思 |
|---|---|
| `hz` | 这一窗**实际**多少拍/秒。标称是 4（`SampleInterval=0.25`） |
| `read_ms` / `pass_ms` | 一拍里**读**占多少 / **整拍**占多少（毫秒，平均） |
| `flush_ms` | `flush()` 占多少 —— 它是唯一会阻塞的调用（里面有 HTTP） |
| `wall_ms` | **客户端给了多少**（两拍之间的实际间隔，平均） |
| `cpu_pct` / `read_pct` | `pass_ms/wall_ms` / `read_ms/wall_ms`。**接近 100% = 采集器把这一帧吃满了** |
| `worst_ms` | 这一窗最坏的一拍 |

**为什么要这几个数：** `dt` 长**一件事说明不了两件事** —— 「采集器吃了这一帧」和
「客户端本来就在卡」在 `dt` 上长得一模一样。`cpu_pct` 高就是前者，`cpu_pct` 很低而 `hz` 还是低
就是后者。S 行行首的 `rd=` 是同一件事的**单拍**版本，用来看长尾。

### 8.1 那个「-431 °F 关机被接受」是噪声

所以它能「成功」，靠的是**等一个足够大的负向抖动**，而不是等一次关机。
**判别器坐在噪声里，于是它量到的是自己的阈值，不是世界。**

### 8.3 所以旧根因是错的

旧版这里写的是：「`Coolant-OFF` 把温度顶回去 → 从没到冷态 → 驱动器卡在

是错的。** 真正的情况是：**那次班次是熔毁 + 配额未达标结束的**

> 「驱动器等 408 秒是因为没人给它冷态」→ 要修的是流程（早点关机、别碰泵）。

> - 第一刀：驱动器按下之后**不再等温度下降**，按下即收工。

>   更没有一个叫「驱动器」的东西去问。**一个不成文的规则最好的归宿是被删掉，

## 13. 另一条通道：客户端状态采集器（`_tools/TRG_original_state.luau`，tag `s2`）

**这一节跟上面 12 节不是一回事 —— 它一台服务器都不要。**

上面那些（`r60` / `w61` / 开机那份）走的是 **8765/8766 两个 HTTP sink**：脚本把字节
POST 到本机、执行器从本机 HTTP 取脚本本体。**这一份不走那条路。** 它跑在**第三个 VM** 里 ——
真正的 Roblox **客户端**进程（不是 Studio），通过一个真 UNC 执行器（`executor=Solara`）。

### 13.1 它写到哪里

**写进执行器自己的文件系统**：`D:\SCRIPT\SolaraV3\workspace\`。那是个**普通的 Windows 目录**
—— Python 和 `cp` 直接往里写/读，脚本里的 `writefile` / `readfile` / `appendfile` /
`isfile` / `listfiles` 打在同一个目录上。所以：

- **不用起 8765**，**不用起 8766**，`start_services.bat` 不用跑；
- 字节**不经过上下文**，全程在盘上；
- 采集器**不需要 `HttpGet` 去取脚本**：脚本本体是你手动放进那个目录的。

### 13.2 怎么注入

1. 把仓库里的 `_tools/TRG_original_state.luau` 拷进 `D:\SCRIPT\SolaraV3\workspace\`
   —— **用 `_tools` 旁边那个部署脚本**（`deploy_state.py`，在会话 tmp 里），它逐字节比、
   核 md5、并断言**零反斜杠**（§0.10）；
2. 在**已经进了原版游戏**的客户端里执行：
   `loadstring(readfile('TRG_original_state.luau'))()`；
3. 产物立刻出现在 `D:\SCRIPT\SolaraV3\workspace\trg_state_<日期>-<时分秒>.txt`。

**先开机再注入，还是先注入再开机？** 两份都行，但**要抓开机那一刻就趁早注入** ——
`GetPropertyChangedSignal('Value')` 只在**真写**时发（同值写不发），所以晚注入 =
让掉它之前发生的那部分。

### 13.3 它记什么

**根是写死的 `Workspace.Stats`**（不是普查 —— 这一份和监视器不同，它钉一个容器）。
客户端上那个容器是：**38 个后代 = 32 个 `ValueBase` + 6 个文件夹**
（`Core` / `CBL1` / `CBL2` / `CBL3` / `Fans` / `HDEF`），32/32 全挂。
**第一行会写 `# hooked 32 ValueBase objects under Workspace.Stats (of 38 descendants)`** ——
这个数**每次跑都要一样**，不一样就是选择器坏了（挂到 0 个时它 `error()`，不交付空日志）。

三种行，**共用同一个时钟**：

| 前缀 | 内容 |
|---|---|
| `[HH:MM:SS] <rel-s> <path> <old> -> <new>` | **记录行**：某个 `ValueBase.Value` 真的变了（同值写不发） |
| `[HH:MM:SS] <rel-s> = <path>=<value> …` | **快照行**：32 个值的全量（每 `Heartbeat` 秒一次，默认 30） |
| `[HH:MM:SS] <rel-s> ~ <Monitor>{…} <AlertsLamps.n/m{…}>` | **面板行**：7 台监视器上画出来的文字 + 警报灯 |

**表头全部以 `#` 开头。** 扫这个文件时**不要把表头当数据** ——
`' -> ' in line` 这种计数器会数到表头里那句 `# record: … <old> -> <new>`（见 §0.20 一族）。

### 13.4 面板 ≠ 状态

**`~` 行读的是屏幕上的字，`=` 行读的是状态。两个可以同时一个准一个不准。**
实测：停堆那一屏 `DescLabel=FATAL SYSTEM ERROR`、`ShutdownText=ENERGY QUOTA MET`，
而同一拍 `Core.TemperatureVal=0`、`GameActive=false`。
**要状态就读 `=` 行；要「玩家看到什么」才读 `~` 行。** 两者都不是对方的替代品。

### 13.5 `AlertsLamps` 怎么读

`AlertsControlRoomMonitor` 上 **39 条 caption 全部 `Visible=true`**、**警报响不响都一样**
（它们是永久标签）。**警报状态在每条背后另一块 Frame（板）上。**
所以 `AlertsLamps.<亮>/<总数>{文字=r,g,b; …}` 数的是**板**：

- 安静时：**`AlertsLamps.0/27{none visible}`**；
- 有警报时：亮的那几块列出来，颜色是**严重度图例**：
  `255,0,0` severe · `170,0,255` malfunction · `255,255,0` active · `255,85,0` caution ·
  `104,255,34` core active · `255,85,255` destabilisation · `0,170,255` stallout · `255,255,255` white。

**「板亮 = 该警报在响」是假设，尚待证实**（一行测试：开机看 CBL ACTIVE / PUMP ACTIVE 亮不亮）。
**不容怀疑的是那条否定**：caption 是死的，所以**只抓文本的快照说不出哪个警报响过**。

### 13.8 同一条通道的另一半：MCP worker 什么时候会掉、怎么知道

**执行器身上有两个分开的东西：一条 WS（它在的）和一个 worker（它可能不在）。**
两者可以同时「连接正常」和「工具全废」—— 实测 2026-10-07（`RobloxPlayerBeta` pid 16248）：

| 现场 | 读数 |
|---|---|
| daemon 进程 | pid 9040，当天 12:56:57 起，听 `0.0.0.0:28429` + `[::]:28429` |
| daemon 服 `mcp.lua` | `curl http://127.0.0.1:28429/mcp.lua` → **HTTP 200 / 125977 字节** |
| 执行器 → daemon 的 WS | `bin\DEBUG.txt` 里每秒一条 `[WS] WS_POLL pid=16248 state=OPEN` |
| daemon 的登记表 | `list-roblox-processes` → **`status: unconnected` / `workerId: null`** |
| 最后一次真的派活 | `DEBUG.txt` 里最后一条 `{"type":"task",…}` = **13:29:37**（全档 **31** 条 `{"type":"task",…}`，跨 13:10:32–13:29:37；`{"type":"registered"…}` 只出现 **1** 次） |
| MCP 工具面 | `resolve-path` / `execute-script` → `No Roblox executor is connected.` |

**所以「WS 是 OPEN」推不出「工具能用」** —— 那只是执行器在轮询它自己的 socket。
**worker 是另一件事**：要有脚本在 Roblox 里跑起来、把 `mcp.lua` 拉下去执行。

**诊断顺序（三步，每步一个读数）：**
1. `list-roblox-processes` —— **`workerId` 有值才叫活**（`unconnected` 别去猜，它就是没有）；
2. 在 `bin\DEBUG.txt` 里搜 `mcp.lua` —— 这一趟 **0 条命中**，说明从头到尾没人取过它
   （**daemon 能服 ≠ 有人取**）；
3. 数 `{"type":"task"` 的最后一条时间，和最近一次成功的工具调用对表。

**`autoexec\` 是自动注入点，但它在「注入那一刻」跑。** 这一趟操作员填的是标准 loader
（`loadstring(game:HttpGet("http://127.0.0.1:28429/mcp.lua"))()` + 一行 print，80 字节，
14:35:45 写入）—— **但写完之后没有任何一次注入发生**，所以 DEBUG 里一条 `mcp.lua` 都没有。

**`bin\UIDEBUG.txt` 帮不上忙，而且它会骗人**：那份只记 SolaraV3 自己的
`periodic check: tick`（5 分钟一次），**一个字都不记脚本执行**。
所以「UIDEBUG 里没有」= **没有信息**，不是「没跑」—— 拿它判注入跑没跑，等于拿一把不量这个的尺子。

#### 13.9.3 命令文件：seq 单调、文件**永不截断**

格式 `^(%d+)%s+(.*)$`，例如 `1 census`、`2 pos`、`13 fire Workspace.X.CDPart`。
执行规则是「**任何 seq 大于上次执行过的**」，于是：

- **可以重复注入**：`trg_drive_state.txt` 存着最后的 seq，重注**不会**把老命令重放一遍；
- **命令文件不清空**：它是「被要求过什么」的**耐久记录**。清空之后一条丢掉的命令
  就**看不见了** —— 丢一条安静的命令和「没写过」在盘上同形（同 §0.18 那一族）；
- 想重跑一条老命令：**写一个更大的 seq**，不要改老的。

#### 13.9.5 每次发火跟一次测量；两种发法**分开记**

`fireclickdetector(cd)` 与 `cd.MouseClick:Fire(lp)` **不是一回事**：前者走执行器的 UNC 实现，
后者只放**客户端**的监听者，而**游戏的逻辑在服务端**。两者在代码里长得一样、效果可以不同，
所以日志记的是**实际用的那一句**：

```
fire MouseClick:Fire                          -- UNC 不在，退化成这样
fire fireclickdetector                        -- 正常
fire MouseClick:Fire (fireclickdetector ABSENT)
fire ERROR <为什么>
```

发火**之前**先 `PivotTo` 把角色挪到该件旁边（`DefaultStuds = 4`，抬高 `RiseStuds = 3`）。
理由写在文件里：**`fireclickdetector` 只发信号、不移动角色**，而任何距离检查看的仍是
**真实位置** —— 隔着一张地图按下去会被**无声拒绝**，没有任何报错。发火之后
`task.wait(SettleSeconds = 1.2)`，再记一行：

```
fire CHANGED  Core.TemperatureVal=... ...
fire NOCHANGE Core.TemperatureVal=... ...
```

那两行是驱动器**自己的** `Workspace.Stats` 读数，不等采集器那 30 秒的快照。

#### 13.9.6 它活着吗；怎么起、怎么停

**活着的证据是 `trg_drive_loop.txt` 的 `mtime`，而且它是刻意单独一个文件。**
循环每 `Poll = 0.5 s` 重写它一行（`now rel= seq= cmds=`）。日志不行 ——
日志是**追加**的，窗口一短就看不出来；§13.6 那条在采集器上量到的教训（一个 30 秒周期的写者，
在任何短于 30 秒的窗口里都是一条平线）在这里同样成立，所以活着的证明必须是
**一个每拍重写的文件**。

**怎么起**：`autoexec\trg_drive.lua` 在**注入那一刻**跑（这是唯一的自动点），
或者手动 `loadstring(readfile('TRG_original_drive.luau'))()`。
那个桩**先写标记、再 load** —— 「从没触发」和「触发了但 load 失败」在盘上本来逐字节相同
（取舍 400），一行标记把它们分开。桩失败会在 `trg_drive_autoexec.txt` 留 `LOAD FAIL <原因>`。

**怎么停**：往 `trg_cmd.txt` 写一句 `stop`（走同一个通道，**留下记录**），
或注入前设 `_G.TRG_DRIVE_AUTORUN = false`，拿到一个**躺着不跑**的模块，需要时 `M.start()`。

### 13.9.8 抗挂机（`d2` 新增，`d3` 加了 `via`）—— 那 20 分钟里 `d1` 什么都没做

**Roblox 大约 20 分钟没有用户输入就踢人**，而 `d1` 里**没有任何东西是输入**：
`PivotTo` 只是把角色挪一点，挂机计时器看的是**用户**，不是角色。所以长班次会以
**会话消失**结束 —— 而**失败是静默的**：后面的命令根本没被执行过，盘上没有任何一行说它没跑。

两条路，**走的哪条记在日志里**（和 `fire` 记「实际用哪句」同一个理由：一个静默的退化和真跑了，
事后必须长得不一样）：

| 路 | 做法 | 备注 |
|---|---|---|
| 1 | `VirtualUser:CaptureController()` + `ClickButton2(Vector2.new())` | 经典执行器抗挂机。这是**游戏内虚拟输入**，**不碰你的真鼠标** |
| 2 | 一个小 `PivotTo`（抬 `IdleJiggle = 0.5` stud） | 退路。它**不重置那个计时器**，只是证明角色还活着 |

**三种触发**，日志行是 `antiidle <哪条路> via <哪条触发> at rel <秒>`：

- **`via timer`**：`M.step()` 每拍检查 `os.clock() - lastInput < IdleSeconds`（**240 秒**，留够几次漏拍）；
- **`via idled`**：`M.start()` 里挂 `LocalPlayer.Idled`，**踢人被宣布的那一刻**就当输入处理；
- **`via verb`**：我手动发 `idle` 命令，用来现场验那条路。

`<哪条路>` 是 `VirtualUser` / `jiggle` / `nil`。
**`nil` 是真的**：两条路都不可用时它照写，一个 `nil` 比一行不写诚实。

**`via` 那一格是 `d3` 补的，理由是被抓到的一次实测**：`d2` 两个调用点写**同一行**，
于是「这次是谁触发的」在盘上读不出来 —— 和「两个 build 都不改 TAG」同一个病。
23:27:39 同刻两行，`140.8 … via idled`（`d3`）与 `744.7 …`（**热重载留下的老 `d2` 实例**），
**除了 `via` 那个词以外逐字节相同** —— 没有它，这两行读起来就是「它同一秒动了两次」（取舍 410）。

### 13.9.9 GUI 那一半（`d2` 新增）—— 为什么按按钮比按 `ClickDetector` 值

`ClickDetector.MouseClick` 的处理函数跑在**服务端**，本地发火到不了它 —— `d1` 那六次
`NOCHANGE` 里始终分不开「按到了但没用」和「根本没按到」。**GUI 按钮是反过来的**：
它的处理函数**一定是客户端 LocalScript**，所以从这里按下去跑的是**真代码**，
它发的 remote **真的到服务端**。停在一张菜单上的游戏，更可能是在**这里**等着。

**三条通道，依次试，并记下谁成了**（这台执行器的信号没有 `:Fire`，
所以顺序是有意义的，而沉默与「按成了」事后必须可分辨）。**三条全断时**实测是这样
（桩里两次 `try` 都是 `nil`，是**一段逐字的运行记录**，不是示意）：

```
press try activated -> nil
press try click -> nil
```

### 13.9.14 `d5` 修的是坐标：`AbsolutePosition` 是 GUI 空间，`VirtualInputManager` 是屏幕空间（Phase 104）

**这是这条通道上最贵的一个洞，而且它一路无话。** `d1`..`d4` 的 `pressAt` 用的是
`ap.Y + as.Y/2` —— 少了 `GuiService:GetGuiInset().Y`。于是**四次按压中没有一次落在按钮上**：
`SendMouseMoveEvent` 返回、按钮事件返回、点击落到那个像素上的别的东西，
而**日志里只有 `NOCHANGE`** —— 和「按钮是死的」逐字节同形。

**机制**（§0.11 那 58 px 的真身）：

| 量 | 空间 | y 从哪量 |
|---|---|---|
| `GuiObject.AbsolutePosition` | **GUI** | **顶栏下面** |
| `VirtualInputManager:SendMouseMoveEvent` / `SendMouseButtonEvent` | **屏幕** | **算上顶栏** |
| `UserInputService:GetMouseLocation()` | **屏幕** | **算上顶栏** |

换算是 `ap + inset + as / 2`，`inset = GuiService:GetGuiInset()`，这台客户端 `(0, 58)`。

**~~两半都要读~~（已更正，见 Phase 105）**：~~`ScreenGui.IgnoreGuiInset == true` 的 ScreenGui
本来就在屏幕空间，再加 inset 就反着错 58 px~~ —— **那个旗只挪 ScreenGui 自己的矩形，
不改变子件 `AbsolutePosition` 所在的空间**，所以 inset 对**每一个** ScreenGui 后代都要加。
实测：带旗的 `ScreenGui` 读 `abs=0,-58 1151x714`，Roblox 自己的 `MouseGui` 读 `0,0 1151x656`
—— **同一条下缘、上缘差 58**，两次读数都在同一套枚举下自洽，**没有任何东西在说谎**。
所以 `clickPoint()` 先问祖先 `LayerCollector` 是什么类，**并且把「这次用的是哪个空间」
当返回值带出来**（`inset+0,58` / `inset+0,58/ignoreinset` / `layout/SurfaceGui` / `nospace`）——
`/ignoreinset` **只是标签**（`d5` 就是把它读成了分支才错的，那两个点**逐位相同**）；
而 `nospace` 是「什么都没量到」，即使它打印了两个看着很对的数。

**`clickPoint(btn)` 是全通道唯一的 rect→点换算**，两个调用点都走它：
`pressAt`（真的点）和 `guiCensus`（只报告 rect）。`guiCensus` 不是缺陷源，
但它给的正是「用来找按钮」的那份读数，**给的却是一个不能直接拿去按的坐标**，所以一起修。
构建器里钉着两条不变量：`as / 2` 全文件**恰好一次**、`clickPoint(` **恰好两个**调用点 ——
**在调用点重推一次就是原来那个 bug，所以长出来的调用点必须让构建失败，不能被漏掉。**

**这条修复是靠 `_tools/build_drive_clickpoint_test.py` + `_tools/selftest_drive_clickpoint.py`
钉住的**（§13.9.10 是同一套做法：构建器**按文本抽出**交付物再塞进桩，自测把换算打坏）。
构建器跑 **12 例**（`C1..C12`；`C1`/`C2` 的矩形取自现场读到的 `PostShiftButton`
`abs=446.600,566.400 size=60.000x60.000`，桩里取整成 `447,566` —— **`C10` 专门守着
「小数要 floor 不要 round」**，所以取整只许发生在**输入**上），
自测 **9/9 变异各自红在指定那条上**、留绿的对照保住、驱动 md5 前=后、`run_tests.sh` **rc=0**。
**对照换过一次位置**：`d6` 下带旗的 case 拿的 inset 和大家一样，所以 `C_IGNORE` 会跟着 `C1`

这两条变异**动不了它们**）。
