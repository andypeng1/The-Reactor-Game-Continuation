## 0. 一句话

**开两个本地服务器 → 注入 → 你自己开机 → 按 DRIVER → 你自己按下关机拉杆 →
文件自己封存。**

> ### ⚠️ 用之前先看 §4.0
> **一次注入就够。** 新班次开局堆芯是**冷的**（你的 A1），所以「开机」发生在班次
> **自己的开头**，「关机」发生在**结尾** —— **两半在同一份文件里**。
> 这一条**推翻了上一版的「必须注入两次」**。
>
> ✅ **D7 已定案（你的回答：「我自己手动关」）。** 上一版这里挂着的是一个警告：
> 「驱动器武装后 60 秒就关机，只会录到 3 分钟」。**那个警告连同那 60 秒一起作废**，
> 因为驱动器现在**根本不按**。你什么时候按关机拉杆，班次就什么时候结束；
> 驱动器只负责把「你按了」和「游戏承认了」两件事分别记下来。

## 1. 开跑前：两个服务器，缺一不可

开两个终端，各跑一条，**都不要关**：

```bash
# 终端 A —— 收数据的（8765）。脚本把字节 POST 到这里，落盘到 Data/flow/
python _tools/receive.py --port 8765 --dir D:/rblxTRGproject/Data

# 终端 B —— 给脚本的（8766）。执行器从这里取脚本本体
python -m http.server 8766 --bind 127.0.0.1 --directory _tools
```

**为什么要两个：** 8765 是**出**（数据从游戏里出来），8766 是**入**（脚本进游戏）。
端口不能混用，两个服务各占一个。

**怎么确认活着：** 终端 A 每收到一段就会打一行 `RECV <名字> <字节数> <crc32>`。
没有这行 = 脚本没在发 = 采集没开始。

**为什么绕这一圈：** 直接把 1.4 MB 数据从 Studio 读回对话里要烧掉二十万 token。
让游戏自己 POST 到磁盘，字节就永远不经过对话。

## 2. 注入（四步）

**执行器：Solara V3。** 加载方式 `loadstring(...)`。

1. 确认上面两个服务器在跑。
2. **SAM 不用你操心 —— 这一步已经从流程里删掉了。**

   ```
   game.Workspace.Consoles.MainReactorConsole.SAMKeyboard.ClickPart
   （只是地址，留在这里给你自己随手用）
   ```

   **D8 已定案（你的原话：「SAM 默认是关闭的，SAM 的开关由我控制，驱动器不用管」）。**
   所以：
   - 记录器**不再**在注入时提示你关 SAM，也不再因为 SAM 开着而写事件；
   - 驱动器**不读** SAM 的状态，也不做任何和 SAM 有关的判断；
   - SAM 是什么状态**完全由你决定**，记录器只在你按注入那一拍把它**记一笔**
     （`EVT SAM ... SAM IS ON at inject` / `SAM is off at inject`），
     因为「当时 SAM 开没开」是事后读曲线时需要的背景，不是操作指令。

   （界面上怎么看：`SAMKeyboard.Light1.NeonPart` 绿色 = 开着，
   或 `MainMonitorFrame.SAMFrame.Visible = true`。见 `QUESTIONS.md` A3。）

3. 在**原版游戏**里用 Solara V3 执行：

   ```lua
   loadstring(game:HttpGet('http://127.0.0.1:8766/TRG_original_recorder.luau'))()
   ```

4. 看控制台，应该出现：

   ```
   [rec] hooked <数字> detectors -> flow/original_<时间戳>
   ```

   然后屏幕**左上角**出现一个小面板（`rec: starting` → 开始刷新数字）。

**`hooked` 那个数字是点击钩子数。** 上次是 1003。如果它是 0 或者很小，
说明 `fireclickdetector` 这个执行器全局不存在（见 §9 排查表）。

## 3. 屏幕左上角那个面板怎么读

```
phase RUN  sample 1234  lines 5678
seg 90  buf 3210 B  fails 0
drop 0  spill 0  evt 1456
drv holding holding  shut 0/2 start 0/1
```

| 字段 | 意思 |
|---|---|
| `phase` | `PRE` 还没确认流程 / `RUN` 运行中 / `DOWN/UP` 已确认关机、等重启 / `UP` 已重启、正在录重启后的稳定段 |
| `sample` | 第几次采样（每秒 4 次，上限 14400 ≈ 1 小时） |
| `lines` | 已经写进文件的文本行数 |
| `seg` | 已经发出去的 HTTP 段数（每段最多 48 KB） |
| `buf` | 缓冲区里还没发出去的字节 |
| `fails` | **连续**发送失败次数。到 12 就转存磁盘 |
| `drop` | 因为缓冲区满了被丢掉的字节。**这个不是 0 就要当回事** |
| `spill` | 因为发不出去而转存到磁盘的字节 |
| `evt` | 事件计数 |
| `drv <状态> <裁决>` | 驱动器现在在哪一步、上一次判断的结论（见下） |
| `shut n/m` | 关机候选：试到第 `n` 个，共 `m` 个。`0/2` = 一个都还没试 |
| `start n/m` | 开机候选，同上 |

**`drv` 的状态机（只会往前走）：**

现在的配置是 `DrivePressControls = false` —— **你不按，驱动器不按**（D7）：

```
arming ─────┬─► watching ──► shut_down ──► done
            │      ▲
            │      └── 你按下关机拉杆，游戏承认 → 走这里（裁决 user-shut）
            │
            └─► cold ──► 等你自己开机（什么都不按，什么都不记）
```

> **`watching` 是现在唯一会停留的状态，而且它可以停一整个班次** —— 想停多久停多久。
> 驱动器在这里**不花任何东西**：不按键、不设时限、不判断温度。
> 它只盯四个信号，**任何一个先出现**就认账：
>
> | 先看到的信号 | 事件里写的理由 |
> |---|---|
> | `v.shutdown == true` | `the shutdown screen is up` |
> | `s.GameActive == false` | `s.GameActive=false` |
> | `s.MainframeMeltdown == true` | `s.MainframeMeltdown=true` |
> | `s.GameFail == true` | `s.GameFail=true` |
>
> 顺序就是这个顺序，因为 `v.shutdown` 是**你 B3 亲口点的那个屏幕**
> （`Workspace.Monitors.MainControlRoomMonitor.Screen.MonitorUI.ShutdownFrame`），
> 它出现得最早、也最贴「操作员刚按下去」这件事。

`DrivePressControls = true`（**备用配置**，保留但不在现在的流程里用）走这条：

```
arming ──► holding ──► press_shut ──► shut_down ──► done
```

> 这条路**代码还在、测试还在**（`bash _tools/run_tests.sh` 会两种配置都跑一遍），
> 只是默认不启用 —— §1.4 第 2 条「不要在没有替代品的情况下删除功能」。

`ShutdownEndsShift = false`（**更远的备用配置**，一次注入录开关两个方向）：

```
arming ──► press_start ──► proving_start ──► holding ──► press_shut
                                                             │
   done ◄── waiting_up ◄── proving_start ◄── press_start ◄── dwell_cold
                                                             ▲
                                            waiting_down ────┘
```

**`drv` 的裁决（卡住时看这个）：**

| 裁决 | 意思 |
|---|---|
| `watching` | **现在的正常态**：驱动器武装好了，在等你开机 / 等你按关机。**停在这里是对的** |
| `user-shut` | **你按下了关机拉杆，而且游戏承认了**（四个信号之一）。这就是现在唯一的正常出口 |
| `holding` | 备用配置里才出现：在跑 `DriveHoldSeconds`，然后它自己去按关机 |
| `arming-cold` | 备用配置里才出现：注入时核心是冷的，它自己替你按 START |
| `shut-accepted` | **驱动器自己按下去了**（只在 `DrivePressControls = true` 时可能） |
| `shut-confirmed` | 游戏承认了关机，而且是**驱动器按的**那一支 |
| `no-shut-control` | 找不到关机控制 |
| `relit-itself` | 核心自己又亮了（低温跳闸后的自恢复？） |
| `start-accepted` | 开机按下去了，而且生效了（核心真的亮了 —— 开机的到达是能问的） |
| `start-inert` | 按了没反应 |
| `no-start-control` | 找不到开机控制 |
| `no-temp-readout` | 温度读不到 |
| `flow-complete` | 整段流程录完了（只在 `ShutdownEndsShift = false` 的长路里会出现） |
| `disarmed-by-user` | 你把 DRIVER 关了 |
| `rearmed` | 你又把它打开了 |
| `off-no-fireclickdetector` | 执行器没有 `fireclickdetector` |
| `errored` | 驱动这一拍抛错了，已经记进事件里 |

> **`user-shut` 和 `shut-confirmed` 是故意分开的两个词。**
> 它们回答的是两个不同的问题：「**是你按的吗**」和「**是驱动器按的吗**」。
> 如果合成一个，这份文件就答不出「这次关机到底是谁干的」——
> 而这正是你唯一一次开关最想问的事。

**已经删掉的裁决**（旧笔记里可能见过）：`cold-at-inject`（拒绝开机的旧行为，
被 D2:A 改成 `arming-cold`）、`shut-inert`（「按了没反应」—— 按下即关机之后，
「有反应」和「没反应」在按下那一瞬间是同一个观察）。
**`shut-accepted` 的含义也变过**：它原来写的是「温度掉了 ≥400 °F」，
那个判据是假的（见 §8）。

另外两个你会看到、但只闪一下的：`off-waiting-arm`（执行器在、但你还没按 DRIVER）和
`unsupported`（arm 之后、第一拍结论之前的那一小段）。
`unsupported` 这个名字其实是旧的 —— 它是一个**兜底值**而不是一个结论，
`drive.on` 为真时它也会短暂出现。我看到了，没动它，因为它不影响任何一个读数的含义。

**按钮（现在是两个）：**

- **`SEAL NOW`**（红）—— 立刻封存，写收据，结束。**任何时候按都安全。**
- **`DRIVER: ON/OFF`**（蓝/灰）—— 驱动开关。**这是那个「只能开关一次」的闸门。**
  关掉只是停止**未来**的按压，不会取消已经按下去的。

**热键：** `RightShift` = 封存（和红色按钮同一个作用）。

> ⏳ **这两个按钮要合并成一个。** 你 Q7 说「按一下开始，再按一下结束并封存」——
> 正是要做的。合并后是：
>
> ```
> 注入后     [  开 始  ]      ← 按一下：驱动器武装，开始这次唯一尝试
> 按下后     [  封 存  ]      ← 再按一下：结束并写收据
> 已封存     [ 已封存 ] 变绿
> ```
>
> **还没做，等你确认。** 那个问题原来记在 `DECISIONS_NEEDED.md` 的 D3，
> 而那个文件已经删掉了 —— **现在所有要你拍板的事一律在 `QUESTIONS.md`。**
> 在那之前用现在这两个按钮：先按 `DRIVER`，结束时按 `SEAL NOW`。
>
> 补一句：合并在**现在这条流程里**已经没有原来那么必要了。原设计假设你要
> 「按一下开始 → 等关机 → 再按一下封存」，也就是**关完之后你还有事要做**；
> 而按下即关机 + 自动封存之后，SEAL NOW 变成一个**只在中途想收工时**才按的按钮。

## 4. 操作流程（你该按什么，按顺序）

### 4.0 先记住这条 —— 它决定了整个流程

> **关机 = 班次结束。** 不管是因为拉杆、低温跳闸、还是熔毁，只要堆芯关了，
> 班次就结束、**不能继续**（你的 Q3 + Q4）。

**而新班次开局，堆芯是冷的（你的 A1）。** 所以：

- 「开机」不是上一场结束之后的事 —— **它就是这个班次的开头**。
- 「关机」是这个班次的结尾。

**两半在同一个班次里，所以一次注入、一份文件就够：**

```
注入（此时堆芯冷）
  → 你手动开机
  → 核心彻底开好
  → 你按 DRIVER          （它从此只看不动）
  → 你自己按下关机拉杆
  → 班次结束  →  文件自动封存 ✓
```

**上一版这里是错的。** 它写的是「关机 = 班次结束 = 会话终止，所以一次注入永远录不到
两半，必须注入两次」—— 那个结论默认「开机」只能发生在**上一场结束之后**，
于是只能落进下一次注入。A1 把那个默认推翻了，**「两次注入」连同 D1 一起作废。**

**仍然成立的那一半：关机之后不能继续。** 所以关机之后**不再重新开机** ——
那个动作会**在一场戏里花掉你唯一的那次开关**，而且发生在客户端被杀前几秒。

---

### 情况 A：正常一次跑完（你要的就是这个）

```
1. 注入（§2 第 3 步）—— 记录器从冷态开始就在录了
2. 你自己按 START（开机拉杆）
3. 让核心彻底开好
   （「开好了」你 B1 给的判据是 quota 监视器的时间越过 12:00PM ——
     记录器现在会把它写进 q.clock / q.up，并在越过那一刻记一条 CLOCK 事件）
4. 按 DRIVER: ON
        ↓
   驱动器进入 watching —— 【它不按任何东西，想让你录多久就录多久】
        ↓
5. 你自己按下关机拉杆（想什么时候按就什么时候按）
        ↓
   驱动器看到四个信号里的第一个 → 记 user-shut
        ↓
6. 班次结束。**文件自己封存** → 面板出现 SEALED，收据写上 ## RECEIPT
```

**第 4 步之后驱动器就只看了。** 它停在 `watching` 不按、不设时限、不判断温度 ——
**上一版那个「60 秒后它自己去按」的常数已经作废**（D7）。所以这一条现在成立：
**只要你不按关机，记录器就一直录**，你想录多久录多久。

**第 6 步不需要你按任何东西。** 自动封存是**零延迟**的：
四个信号里任何一个第一次出现的那一拍就封。

> ⚠️ **按下关机之后，文件不一定马上就封存。** 「立刻关机」是堆芯的响应，
> 而**游戏宣告班次结束可以晚很多** —— 上次是 **按下之后 414 秒**
> （t=326.71 按下，t=740.33 才等到 `s.GameActive=false`，中间夹了一次熔毁）。
> 所以第 5 步之后请真的**什么都不要做**，也不要因为面板没变绿就去按 SEAL NOW：
> 那个 414 秒的空档**正是这次要录的东西**。
>
> ⚠️ **但如果你按了很多下都不封存**，说明那 414 秒可能不是每次都发生 ——
> 那就看 `drv`：还在 `watching` = 游戏还没承认；已经 `shut_down` = 承认了，在等收据。

> **冷态时驱动器不替你按 START 了。** 旧行为（`arming-cold`，20 秒后自己按）只在
> `DrivePressControls = true` 的备用配置里。现在你还没开机就按了 DRIVER 的话，
> 它进入 `watching` 然后**什么都不做**，控制台会打两行：
> ```
> [rec] DRIVER: the core is cold. Light it when you are ready;
> [rec] DRIVER: nothing is pressed and nothing is spent.
> ```
> 那两行是**故意设计的**：它在告诉你「我在这里等着，不花你的开关」。

### 情况 B：中途想停 / 想早点封存

按 `SEAL NOW`（或热键 `RightShift`）。**它立刻写收据然后停止。**

> ⚠️ **它只封存，不关机。** 堆芯还在跑、班次还没结束，但你手上已经有文件了。
> 这一条**没有变**：D7 定的是「驱动器不按」，不是「SEAL NOW 变成关机」。

### 情况 C：不小心关机了 / 想重来

关机 = 班次结束 = 这一轮结束了，**不能继续**（你的 Q4）。
必须**开一个新班次**（重新加入 / 新服务器），再注入一次。

**好消息：这现在不算「重来」。** 新班次开局就是冷的（A1），
所以「再来一次」= **情况 A 的第一步**，不需要任何特殊准备。

## 5. 温度模型（**重要**）

**堆芯是两头跳闸的：太高会关机，太低也会关机。**

| 阈值（华氏 °F） | 是什么 | 记录器怎么用 |
|---|---|---|
| **2000** | **低温跳闸线** —— 低于它堆芯自动关机（你的 Q1） | 封存判定的**兜底之一**，**且要求先看到堆芯运行过**（见下） |
| **5600** | 游戏自己的状态边界 | **RUN / DOWN 的分界线**（比 2000 早，是「正在掉下去」的信号） |
| 17500 | 游戏自己的状态边界 | 只记录，不驱动 |
| 29500 | 游戏自己的状态边界 | 只记录，不驱动 |
| **39000** | **熔毁线** —— 高于它熔毁（你的 A2：**熔毁条件只有这一条**） | **熔毁判定 + 封存触发** |

**两条线分工不同，别混：**
- 温度**高于** 5600 → 「核心在运行」
- 温度**低于** 5600 → 「核心正在掉下去」（**这是趋势，不是结论**）
- 温度**低于 2000** → **低温跳闸 → 关机 → 班次结束**（**这是结论**）
- 温度**高于 39000** → **熔毁 → 关机 → 班次结束**（**这是结论**，A2 说这是唯一的熔毁条件）
- 连续 3 次采样都低于 5600 → 才翻 `PHASE2 DOWN`（防抖）

> ⚠️ **「跳闸」和「熔毁」都要求「先看到堆芯跑起来过」。** 因为 A1 说**新班次开局
> 堆芯是冷的** —— 冷堆按定义就在 2000 以下。纯看数值（level）的判定会在你注入后
> **2 秒就把文件封掉**，里面什么都没有。所以温度那两条**必须先看到温度上过 5600**
> 才允许触发；旗标类（班次结束 / 班次失败 / 熔毁）一律**按变化**（edge）读，不按数值读。
>
> 这一条是本轮最重要的正确性决定，而且**有测试盯着**
> （`_tools/build_end_test.py` 的 E2，用 `_tools/selftest_end_test.py` 证明过它会红）。

> **低温跳闸 = 关机 = 班次结束。** 见 §4.0。
> 核心在跑的时候**别让它自己凉下去** —— 你一让它掉破 2000，
> 班次就结束了，而且**不是**以你要的那种方式。

**实测数字（2026-09-26 那次）：**

```
按下 SHUT        t=326.71   tempF=9377
（旧版这里写着「关机被接受 t=335.37，8.7 秒 / -431 °F」—— 假的，见 §8.1）

## 6. 数据在哪 / 什么时候算成功

**位置：** `D:\rblxTRGproject\Data\flow\original_<年月日>-<时分秒>`
（文件名前缀是 `Config.NamePrefix = 'flow/original_'`）

**成功 = 文件最后一行是 `## RECEIPT`。** 没有这行就是**没封存**，数据不完整。

```
## RECEIPT name=... samples=... lines=... events=... segments=...
   postfails=... spilled=... dropped=... flow=true/false
   drive=<状态>/<裁决> readouts=... hash=xxxxxxxx over=... kinds ...
```

- `flow=true` —— 记录期间**见过核心从运行状态掉下来**（`sawDown` 落地）。
  判据的线是 `CoreThresholds[1] = 5600 F` —— 游戏自己的 stallout 线（`INGAME_MANUAL` 87：
  「Stallout Possibility will occur if the core temperature is below ~ 6000F」），
  **不是** 2000 F 那条低温跳闸（`Q1`），两件不同的事。
- **`flow=false` 读作「没见它掉下来过」，不是「数据丢了」，更不是「这一份里核心从没冷过」。**
  `sawDown` 要先 `flowArmed`，而 `flowArmed` 要 `isRunning`（`tempF >= 5600`，也就是
  `m.temp` 有读数）连续 `DebounceSamples = 3` 拍 —— **核心还没开起来的时候这个门根本不开**。
  所以**冷启动的一趟在结构上永远给不出 `flow=true`**。`2026-09-26 23:00` 那一份核心冷了
  88 秒（`B 1 t=1.34` 三个 `s.Core.*` 全是 0，`EVT2072–2078 CLICK StartUpLever` 就是开机），
  `flow` 照样是 `false`。
  **冷启动的证据在 `s.Core.TemperatureVal`，不在收据这个字段里。** 见下。

### 温度要看哪一列（2026-09-26 加，Phase 49 量出来的）

**两条序列是互补的，各自只覆盖一半，而且它们接得上：**

| 序列 | 覆盖 | 性质 |
|---|---|---|
| `s.Core.TemperatureVal` | t≈0 → **t=97.90**（0 → 9420 F，≈98 F/s），之后**冻在 9420 不动** | 游戏自己的**状态** |
| `m.temp` | **t=98.77** → 结束 | 监视器上的**标签**，监视器没开机时读 `ERR F` |

接缝处的证据：`s.Core` 最后一拍 t=97.90 是 **9420**，`m.temp` 第一拍 t=98.77 是 **9330**
—— 90 F / 0.87 s = **103 F/s**，和那 98 F/s 同速。**两边对得上，所以两段都可信。**

**`m.fluct` 就是那一 tick 的温度增量**（391/393 行满足
`temp(下一拍) − temp(这一拍) == m.fluct`，逐字节相等）：
`temp` 是 `fluct` 的累加。**tick ≈ 1.8 s**（间隔中位数 1.79、众数 2.0），
`m.temp`/`m.press`/`m.fluct` 三个标签同一步一起变。
**别拿「每采一次」当时间步去算导数** —— 那是在拟合重绘时刻表。

**这一趟量出来的增益（F/tick，1 档冷却、只在 cblPct=75 那条带里可信）：**
`ΣcblPct` **+5.05/%**、每台冷却泵 **−58**、每个风扇 **−33**，当前温度项 **≈ 0**
（也就是**温度不回正，是个积分器**）。**别外推**：冷启动那段 CBL 输出 300%，
实测只有 +180 F/tick，线性模型给 +1104 —— **差 6 倍，这个关系是饱和的。**
噪声 sd ≈ 145 F/tick，**lag-1 自相关 0.655**（不是白噪声）。详见 `PROGRESS.md` Phase 49。
- `drive=<状态>/<裁决>` —— 驱动器最后停在哪。**一次正常的跑完是
  `shut_down/user-shut`** —— **你**按的。这个词答的是「谁按的」，所以它**不会被改写**；
  如果停在 `watching`，说明**游戏到现在都还没承认班次结束**，那才是真的没走完。
  （更旧的版本是 `done/flow-complete`。**故意不叫 `done`**：
  `done` 会立刻封存，把停机之后那几秒的收尾 —— 停机画面和最终温度 —— 切掉）

> **`user-shut` 和 `shut-confirmed` 的分工（这条修过一个真 bug）：**
> `shut-confirmed` 的意思是「**驱动器按的**，而且落地了」，只属于那条备用配置。
> 它曾经被错误地盖在 `user-shut` 上面 —— 你按下之后一拍，收据就变成
> `shut-confirmed`，也就是**在一次驱动器根本没按过的跑里，声称驱动器的按压落地了**。
> 状态断言一条都没红，只有裁决看得出来。现在：**谁按的，裁决就是谁的，不会被改写。**

**你会看到的 DRIVE 事件（正常一次跑完，最多三条）：**

```
DRIVE armed, core running; the driver presses nothing -- press the shutdown lever when the shift should end
DRIVE the operator shut it down: the shutdown screen is up          ← 你按下那一拍
DRIVE the game confirms the shutdown: s.GameActive=false            ← 之后游戏正式结束班次
```

> 第二条和第三条**名字不同就是重点**：第一条是你按的证据，
> 第三条是**机器自己正式宣布班次结束** —— 上次它晚了 **414 秒**，而它正是这次要录的东西。
> 如果第三条一直没出现，说明**班次到你录完为止都还没正式结束**，那本身就是结论。
>
> **同一个信号不会写第二遍。** 这是「只记变化」那条原则在事件上的样子：
> 已经写下来的那个信号，再看到一次不再写。所以第三条**只有出现新信号才会有** ——
> 没有新信号，就只有两条。

- `hash` + `over` —— 收据覆盖的字节数里的 djb2 哈希。**`hash` 只覆盖收据以上**
- `kinds` —— 各类事件计数，一眼看出缺了什么

**封存现在在这些情况发生（按判定顺序）：**

| 原因 | 触发 | 延迟 |
|---|---|---|
| `shift over (GameActive true to false)` | 班次结束的直接信号 | **零延迟**，就在看到它的那一拍 |
| `shift failed (GameFail false to true)` | 班次判失败 | 零延迟 |
| `machine room meltdown (MainframeMeltdown false to true)` | 熔毁旗标翻起 | 零延迟 |
| `cold trip (under 2000 F for 8 polls)` | 低温跳闸，**且堆芯运行过** | 2 秒 |
| `core meltdown (over 39000 F for 8 polls)` | 温度**真的**超过 39000（A2 的那一条） | 2 秒 |
| `held down 40 polls with no end signal` | 核心下去了但一直没信号 | 10 秒 |
| `GameActive false for 40 polls` | 进来的时候班次就已经结束了 | 10 秒 |
| `flow complete` | 整段流程走完（新流程下基本不会走到） | — |
| `sample cap reached, down=...` | 采到 14400 次（≈1 小时） | — |
| `user seal` | 你按 `SEAL NOW` 或 `RightShift` | 立刻 |
| `startup failed: ...` | 脚本自己崩了 | — |

### ✅ 上一版那个「39000 对不上」的疑点 —— 已解决（D9）

> **上一版这里挂着一个没查清的疑点：** 熔毁旗标 `s.MainframeMeltdown` 在 t=719.86 翻，
> 而那一刻监视器只有 **~13000 °F**，可 A2 说熔毁的条件「就这一条：温度 > 39000」。
>
> **你给了答案：** `MainframeMeltdown 是机房熔毁又不是核心熔毁`。
> 所以那根本不是矛盾 —— **它们本来就是两件事**：
>
> | 原因字符串 | 说的是什么 | 证据 |
> |---|---|---|
> | `machine room meltdown (...)` | 机房熔毁，**旗标翻起就算** | t=719.86 旗标翻，温度 13000（不相干） |
> | `core meltdown (over 39000 F for 8 polls)` | **核心**熔毁，A2 的唯一条件 | 要真的读到 >39000，且连续 8 拍（2 秒） |
>
> **上一版那条规则把两件事写成了一件事**，于是把一次「机房熔毁」写成了一次
> 「39000 度的核心熔毁」——**那次核心熔毁根本没发生过**。
> 一份收据上写错原因是比不写原因更糟的事：它是读者不再自己复核时唯一会信的那一行。
>
> **顺带修好了一个更大的问题：** 拆分之后，`Config.MeltdownF`（39000）
> **终于有读者了**。在此之前它是配置里一个没人看的常数 ——
> 因为「核心熔毁」那条规则一直被机房的旗标顶着。两个方向现在各有一条臂：
> 冷端 `LowTripF`（2000），热端 `MeltdownF`（39000），**都带 8 拍的驻留**。

> **为什么两条臂都要驻留（8 拍 = 2 秒）：** 单次读数不能定案。
> 温度是会抖的，一拍 40000 就封存等于把一个毛刺当成了一次熔毁。
> 这跟冷端那条是同一个理由，测试里两条都钉了「少一拍不响」。

### ✅ 缺陷①（上次丢掉收据的那个）—— **已修**

**上次发生了什么：** 文件写到 t=740.33 戛然而止，**`## RECEIPT` 没写成**。
脚本**看到了** `s.GameActive=false`（就在最后一个样本上），
但**没有任何规则去看它**，而且它判定得排在很后面 —— 脚本死在它后面那个 `task.wait` 里。

**现在的做法：** 新加的 `endReason()` **在每轮循环体的第一件事**就判定，
`GameActive` 由 true 变 false **零延迟封存**。

**为什么是 2 秒而不是 5 秒：** 不是随手定的，是上次的实测逼出来的：

| 事件 | 时刻 |
|---|---|
| 温度跌破 2000 °F | t ≈ 739.7 |
| `GameActive` 变 false | t ≈ 740.33 |
| 客户端被杀 | t ≈ **740.33** |

**「跌破 2000 之后再等 5 秒」= t ≈ 744.7，比客户端死亡晚 4.4 秒** ——
那条兜底在上一场**根本来不及触发**。所以 zero 延迟 + 2 秒。

> **别再把它「优化」成多个信号互相印证。** D4 的字面意思（「三条信号一起，
> 谁的窗口先到就谁封」）听起来像**要求信号一致**，而那种写法的自然实现是
> 「关机信号 **且** 先看到核心下来」。**变异测试里第三条就是这个 ——
> 它会让 E1 变红。封存宁可早，不可等。**

## 7. 文件格式速查

**只记变化。** 没变化的采样不占一行 —— 这是设计，不是丢数据。

| 行 | 格式 | 意思 |
|---|---|---|
| `B` | `B <sample> <t> <key=value ...>` | **基线**，开头把所有读数的初始值铺一遍 |
| `S` | `S <sample> t=<秒> dt=<毫秒> <key=value ...>` | 有变化的那一次采样 |
| `EVT<n>` | `EVT<n> <种类> <内容>` | 事件 |
| `PHASE<n>` | `PHASE<n> <名字> t=<秒> ...` | 阶段翻页 |
| `## RECEIPT` | 见 §6 | 封存收据，**最后一行** |

**键的前缀：**

| 前缀 | 意思 |
|---|---|
| `m.` | 主监视器的读数（`m.temp` `m.press` `m.fluct`） |
| `c.` | **控制**状态（`c.cbl1On` `c.cbl1Lvl` `c.fanCount`） |
| `s.` | 系统/服务状态（`s.GameActive` `s.Core.RadiationVal`） |
| `z.` | 汇总（`z.systems` `z.parts`） |
| `r.` | 反应堆相关读数 |
| `t.` | 屏幕上的文字部件（`t.MainMonitorFrame.TempLabel`）。**同一个值往往在好几个监视器上各有一份**，所以会有 `t.` / `x.` 两组重复 |
| `x.` | 屏幕文字的别名路径 |
| `v.` | **屏幕 `Visible`**（`v.shutdown` `v.detonation` `v.boot` `v.error` `v.malfunction` `v.revive`）。**字写在隐藏 frame 上、靠翻 `Visible` 拿出来显示** —— 原版的关机/开机/熔毁提示全是这个形状。见 §11 ⑥ |
| `log.panel` | 设施事件日志面板的**整块快照**（排序、无行号、一行） |
| `fc.panel` | 子空间预测面板快照 |
| `q.panel` | 配额进度面板快照 |

**`q.` 下面三个新键（B1 那条「怎么算开机了」）：**

| 键 | 是什么 | 什么时候写 |
|---|---|---|
| `q.timeText` | 配额监视器上时间那格**原本的字符串**（`TimeLabel.Text`） | 只要它变了就写 |
| `q.clock` | 从 `12:00PM` 起算的**分钟数**（正向走的 12 小时盘） | **只在字符串解析成功时**才写 |
| `q.up` | `q.clock > 0` —— 「开机了」 | 同上 |

> **`q.up` 在正 12:00 PM 那一分钟必然是 `false`。** 12 小时盘把正午放在 `0`，
> 而 `q.up` 是 `mins > 0` —— 所以整个表盘上**只有「12:00 PM」这一分钟**读 false，
> 其余 1439 分钟全是 true。这是判据的形状，不是噪声。但它**不能**用来判断
> 「正午附近是不是班次边界」：正午是 **Equinox 事件的起点**
> （`INGAME_MANUAL` 114/148 原文「12PM marks the beginning of the Equinox Event」），
> 班次是 6AM→6PM（`DECISIONS` 28），**正午在班次正中间**。

> **为什么要三个，而不是就写一个布尔值。**
> `q.up` 是**结论**，`q.clock` 是**结论的依据**，`q.timeText` 是**没被解读过的原始读数**。
> 如果记录器只写 `q.up`，将来发现判据错了（比如那个时钟不是 12 小时盘、
> 或者它到某一点会回绕），**这份文件就再也回不去了** —— 没人能从一个布尔值里
> 重建出原始字符串。三个都留着，判据就永远可以事后重算。
>
> **解析失败就一个都不写**，而不是写个 `false`：`false` 的意思是「读了、算出来没开机」，
> 和「没读懂」是两件事，混起来之后这一列就不可信了。
>
> **`CLOCK` 事件什么时候记：** 第一次读到时间时记一条（那是一句**状态**，
> 不是一次到达 —— 如果你注入的时候班次已经开了，它会如实这么写）。
> **之后分两种，取决于注入那一拍读到的是什么：**
> - 注入时读到**还没开机**（`q.up=false`）→ 第一次 `q.up` 变 true **就是班次开始**，
>   记 `the clock passed 12:00PM: the shift has started`，控制台也打一行；
> - 注入时读到**已经开机**（`q.up=true`）→ 盘已经越过正午了，它得**绕满一圈**才会
>   再读到「过了正午」，所以后面每一次跳变都是**表盘在走**，记
>   `the clock moved to <原文> -- the dial, not a shift boundary: the core was already up at inject`。
>
> **为什么必须分开，而且为什么这是修出来的。** `2026-09-26 23:00` 那份是**中途注入**的，
> 记录器当时在**班次正中间**连着记了
> `the clock is back at 12:00 PM` 和 `the clock passed 12:00PM: the shift has started`，
> 两句隔 60 秒，**两句都是假的** —— 那 60 秒里 `m.temp` 从 12865 走到 12979 F，
> 什么都没结束、什么都没开始。麻烦在于**第二句和真事长得一模一样，因为它就是真的那次越过**；
> 唯一能区分的是注入那一拍的状态，所以那个状态被留着
> （`clockStartedUp`，见 `_tools/build_clock_test.py`）。
>
> **修法只改措辞、不删读数。** 原文照样发，`q.clock` / `q.up` 照样由 `readQuota` 写，
> 所以那一刻仍然在文件里、仍然可以事后捞出来。**拒绝过度解读一个读数，
> 和把它丢掉不是一回事** —— 这一点上面「为什么要三个」那段早就料到了
> （原话：「或者它到某一点会回绕」），也正是因为原始字符串一直在，
> 这次回绕才能从文件里被认出来而不是被猜出来。

**事件种类：**

| 种类 | 意思 |
|---|---|
| `CLICK` | **本客户端看见的一次点击**（有标签，如 `Coolant1-OFF`） |
| `UNATTR` | **值变了但本客户端没看见点击** —— `UNATTR c.cbl1Lvl 2->1 (last click 41 polls ago)` |
| `TMAP` | 屏幕文字路径登记 |
| `TEXT` | 某块文字变了 |
| `ANIM` | 一个 label 在**一次采样内**变了太多次 → 判为动画，丢弃 |

## 8. 上次为什么失败（2026-09-26，值得读一遍）

所以它能「成功」，靠的是**等一个足够大的负向抖动**，而不是等一次关机。
**判别器坐在噪声里，于是它量到的是自己的阈值，不是世界。**

### 8.2 `s.GameActive` 在按下之后又活了 414 秒

这是推翻旧根因的那一条。整个 1.4 MB 文件里 `s.GameActive` **只出现两次**：

```

line 3503   S 2490  t=740.33    false     ← 最后一个样本
```

**t=326.71 按下 SHUT 之后，它一直是 `true`，整整 414 秒。**

### 8.3 所以旧根因是错的

旧版这里写的是：「`Coolant-OFF` 把温度顶回去 → 从没到冷态 → 驱动器卡在
`waiting_down` 等了 408 秒」。

**前半段（泵被关了、温度没掉下去）是真发生的事。把它当成驱动器等 408 秒的原因，
是错的。** 真正的情况是：**那次班次是熔毁 + 配额未达标结束的**
（`MainframeMeltdown` 在 t=719.86 亮，配额未达标的字在 t=740.33 出现），
而**驱动器等的那个「冷态」从头到尾没有来过，也不需要来**。

> **两种说法在这里分岔，而它们的后果完全不同：**
> 「驱动器等 408 秒是因为没人给它冷态」→ 要修的是流程（早点关机、别碰泵）。
> 「驱动器**本来就不该等**」→ 要修的是**驱动器**。
> **后者才对**，因为按下关机拉杆就是立刻关机（你的原话）。
>
> **改了两轮，D7 是第二刀。**
> - 第一刀：驱动器按下之后**不再等温度下降**，按下即收工。
> - 第二刀（D7，现在）：**驱动器连按都不按了** —— 关机拉杆由你按。
>   所以「它等不等冷态」这个问题现在**没有发生的机会**：它没有按压这个动作，
>   也就没有任何「按完之后」的阶段。

### 8.4 那次到底是谁关的冷却泵

`UNATTR` 事件数是 **0**，说明每次变化背后都真有一次点击被看到，也就是发生在
你自己的客户端里。**最可能还是 SAM**（`Q6` 那个 `SAMKeyboard` 开关管的自动操作 AI）：

### 8.4b 那个「SAM 和关机对抗了 408 秒」的故事 —— **已撤回（D8）**

**上一版这里讲了一个因果故事：**「SAM 在关机之后把冷却泵关掉，把温度顶回去，

## 11. 缺陷台账（哪些修了、哪些没修）

### ✅ ① 游戏结束时不会自动封存 —— **已修**（上次丢收据的直接原因）

**顺带修掉的一个更隐蔽的：** 旧代码把它判定得排在循环很后面 ——
即使有这条规则，它也会晚一拍。现在 `endReason()` 是**循环体里的第一件事**。

### ✅ ② `fc.panel`（子空间预测面板）是瞎的 —— **已修，待现场确认**

全场只发了 **1 次**快照，内容只有 `AnnouncementText=HADEN THRESHOLD BREACH ~3:00 AM`。

EVT1503 ANIM ...ForecastControlRoomMonitor.Screen.MonitorUI.
         MainMonitorFrame.ScrollingFrame.TimeSliceTemplate.TimeLabel

这是这次改动里**最可能解释「立刻关机」为什么没被记到**的一条。

改之前，记录器把**文字**录得到处都是（`Text` / `TextLabel` / `log.panel` / `q.panel`…），
