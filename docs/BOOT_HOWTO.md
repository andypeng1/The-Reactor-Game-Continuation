### 1.1 追加上去的两个**代价**，写在这里而不是藏在注释里

1. **合并（coalescer）**：信号里只记账，**4 Hz 的 tick 才写行**。所以
   **在一个 tick 内改了又改回去的值，不会被记下来**。这是去掉 99.4% 噪音必须付的钱
   ——你原来那份是在**事件**里写的，所以它记得住，也所以它 1.16 M 行。
   （登记时会把当前值**播种**成基线，所以「一直是 false」的键不会在第一次 tick 冒出一行。）
2. **`.GlitchEffect` 这段路径的几何属性**一律不记。**只有几何**：它的
   `Visible` / `Image` / 颜色照记。这条粒度是 Phase 66 逼出来的——开机屏自己那 0.2%
   才是你要的，而它和那 99.4% 在**同一个文件、同一个 ClassName** 里，
   所以只能按**路径**分，不能按类型分。

---

### 1.2 `b2`：**出生记录**（第一趟实测逼出来的）

上面的「播种成基线」有一条反例，第一趟就撞上了：**游戏是先把消息文本写进克隆出来的
帧、然后才把它挂进树里的**。于是那个实例第一次被看见时，文本**已经在里面了**——
登记把消息本身播成了基线，之后再没有任何变化能跟它不同。

后果，用第一趟的字节说话：`ScreenChanges.txt` 有 **5156 行**，
里面有日志面板那三格的**透明度渐隐**（`TemplateLogFrame1/2/3` 的
`BufferFrame` / `Frame` / `Frame2` / `TextLabel` 共 104 行），
而 **`Text` 一行都没有**——**开机自己的旁白，正是最该抓到的那部分**。

所以 `b2`：**运行期新登记的实例，把它的值当数据写出来，而不是当基线播掉**
（`register(obj, true)`，登记时把该键的基线设成 NUL 哨兵并在下一个 tick 写真实值）。
初始那次全树普查仍然静默播种（那是「改了又改回去不算数」这条规则的全部）。
代价写在明处：**运行期克隆出来的一棵子树会多写一遍它被监视的属性**，
并且**出生和下一次 tick 之间发生的改动会按 tick 那一刻的值报出**（全文件都是这个 0.25 s 量化）。

### 1.3 `b3`：**路径不是实例**（第二趟实测逼出来的）

`b2` 修对了，但只修到一半，而**第二趟真机把这个「一半」量出来了**。

键是 `完整路径|属性`。原来的判断是「**这条路径我见过吗**」：
见过就整条跳过——不挂信号、不记出生。于是**同一个路径上第二次出生的实例根本不存在**。
日志面板干的正是这件事：**每条消息都克隆一个**新行**，复用那三个固定名字**
（`TemplateLogFrame1/2/3`），行渐隐完就被销毁，下一条消息又是一次新的出生。

后果，两套仪器对同一件事的说法（同一趟班次）：

| 仪器 | 它数到的日志面板消息 |
|---|---|
| 这一份（`b2`） | **3 条**（`TemplateLogFrame3/2/1` 各一次出生） |
| `r60` 采集器（同一趟的 `Data/flow/original_261002-140019`） | **35 条不同的消息**，含 `START-UP COMPLETED` |
| `w61` 监视器（同一趟的 `Data/originalwatch/261002-140021`） | 那三格被销毁 **47 次**（12 + 27 + 8 个不同实例） |

`3` 是这一份的**测量缺陷**，不是那个面板的行为。
本文件里那条「见过就跳过」的路径门是**唯一**能解释它的机制，
而 `b1` 只有 0 条、`b2` 有 3 条（每格**第一条**），也正对得上。

所以 `b3`：**同一个路径上出现新实例时，把键重新指向它**——
断掉旧实例的连接（否则一条死连接会继续往一条它已经不占的路径上写，
产物就会报出面板从没显示过的消息）、挂新实例的信号、把出生记录重来一次。
`keys[key]` 与 `writes[key]` **故意保留**：每键预算是**按路径**记的，
因为 `suppressed.txt` 的账本写的就是路径。

**这一条也顺手修掉了本文件自己的一处说谎**：文件第 2 行的头注释还写着 `(build b1)`，
而 `CONFIG.Build` 已经是 `b3` —— 产物自报的名字是代码里的那个，所以两趟都是对的，
只有注释在撒谎。**散文说的谎和代码说的谎一样贵**，跟着一起改掉了。

## 3. 注入（**开机之前**，这是唯一有时序要求的步骤）

在 Solara V3 的执行器里，一行：

```lua

```

**必须在按开机键之前注入。** 整个捕获的 `t=0` **就是那一按**（和 Phase 67 里
你那支 hook 钉住的同一个事件）。开机之后才注入 = 没有 `t=0`，前面那段让掉了。

**和监视器可以同时注入。** 两边没有全局变量冲突，产物路径不重叠
（`originalboot/` 对 `originalwatch/`）。**唯一撞的是热键**，见 §5。

**注入前核这三个数**（不要核时间）：

| | **`b3`（当前）** | `b2`（第二趟跑过） | `b1`（Phase 70 交出去的那份） |
|---|---|---|---|
| 字节 | **45200** | 42056 | 38609 |
| 行数 | **941** | 886 | 835 |

## 6. 它什么时候会自己停

| 原因（`meta.txt` 里 `reason=`） | 触发 |
|---|---|
| `noon` | 表盘读到 **`12:00 PM`**（`Monitors.QuotaControlRoomMonitor.…MainMonitorFrame.TimeFrame.TimeLabel`） |
| `ceiling` | 全文到了 24 MB |
| `error` | 结构性问题（没有 `Workspace.Monitors`、没有那个 `ClickDetector`） |
| `hotkey` | 你按了 `RightControl` |

**`wrap` 没有了，这是第一趟量出来的（`b1` → `b2`）。** 原来的理由是「表盘开盘就是
`12:00 AM`，所以离开过它之后再倒退回 `12:00 AM` 才是收盘」。实测与此相反：

| 时刻 | 表盘 | 那一拍**别的地方**在发生什么 |
|---|---|---|
| `t0` = 13:31:01 | 那一按 | — |
| `t≈18 s` | **`11:51 PM`** 是**第一个读数** | 于是「离开过开盘值」这个保险**在第一次读数就被解除了** |
| `t≈88 s` | `11:59 PM` | 温度 248 F、输出 0 GW/H、HDEF 5 % |
| `t≈95 s` | 跨到 **`12:00 AM`** | **点火**：温度 248 → 9478 F、输出 0 → 146 GW/H、HDEF 5 → 99 %、热工监视器 `AUTO RECALIBRATION IN PROGRESS` |
| `t=94.93 s` | — | `b1` 在这里封存（`reason=wrap`），**捕获被一条在班次开盘处触发的规则切断** |

开机链的 `START-UP COMPLETED` 在四趟实测里落在 **86..146 s**（中位 109），
所以 `b1` 那一刀**大概率切在链子结束之前**。

现在：**午夜只留一行注释 `# MARK midnight …`，不封存**（那个时刻本身是有用的锚点，
丢掉它是另一种缺陷）；**正午照旧封存**——那是你自己给监听窗口定的终点
（Phase 62：「按下开机按钮时开始监听…12PM 结束」）。

一条仍要记住的事：**午夜的语义是量表盘量出来的**，不是我从 Wiki 推出来的。
如果哪天表盘的开局值变了（不同 world / 不同版本），第 2 行那格就不再成立——
**先看 `# MARK` 在不在、在什么时刻**，再决定要不要改。

**第二趟（`b2`，`Data/originalboot/261002-140017/`）把这条从「大概」变成了「看见」：**
那一按落在 **11:51 PM**，午夜在 **t≈95 s** 到，然后捕获**继续记了 5 分多钟**
（`elapsed_s=428.82`，最后一行 14:07:44），`# MARK midnight` 只出现**一次**。

同一份产物顺手把表盘的**速率**量出来了（**318** 次
`QuotaControlRoomMonitor…TimeFrame.TimeLabel` 的 `Text`；
另有一格同名的是 `ForecastControlRoomMonitor` 的预报切片，**只 1 次，别把它算进来** ——
`grep 'TimeLabel\]<-C:\[Text\]'` 会给你 **319**），
而我上一轮**猜错了**它：

| | 实测 |
|---|---|
| `14:00:54` | `11:51 PM` —— 第一个读数 |
| `14:02:10` | `12:00 AM` —— 9 个表盘分钟用了 76 s（均值 ≈8.4 s/表盘分钟），**而单步间隔在 2..23 s 之间跳**，不是恒速 |
| `14:02:10` 之后 | **恰好 1 表盘分钟 / 真秒**，一路保持到最后一个读数 |
| `14:07:22` | `5:08 AM`（收工前最后一次读数） |

所以「午夜后 1 表盘分钟/真秒」是对的，**我此前按「8.75 s 恒速」外推到正午的
「≈105 分钟」是错的**（按 1 s/表盘分钟算，午夜到正午只剩 ≈7 分钟真实时间）。
`w61` 注释里那句「roughly thirteen real minutes」指的是同一件事，方向是对的。

## 7. 行格式 —— **冻结的，别改**

```
Time:[HH:MM:SS]<-O:[完整实例路径]<-C:[属性名]<-V:[新值]
```

**两端都锚定**（`^Time:\[…\]$`）。这不是风格问题：`_tools/_attic/scratch/` 里
**七个旧分析器** 编译的是**逐字节相同的**这一个正则，而且**行尾加字段不是向后兼容的**
——`V` 那组是贪婪的 `(.*)`，任何追加的字段都会被吞进 `V` 里，正是行尾的 `$` 在告诉读者「这行完了」。

所以这一份**新的东西一行都不往这个格式里塞**：要么是新的一行、**以 `#` 开头**
（读者全都跳过），要么是新文件。

这条不是靠我记着的：`_tools/verify_boot_capture.py` 会在回归里**从七个分析器自己的源码里
把这个正则读出来**，并要求它们**七个完全一致**，再拿它逐行验捕获。
重抄一份在这里的副本会在读者改掉之后**继续绿**，那正是它要抓的东西。

  **没有任何场景覆盖**——而它正是第一趟真机切断捕获的规则。场景现在是按
  **实测的形状**摆的：`11:51 PM → 11:59 PM → 12:00 AM`。

  **和上一条合起来是一句话：测试台只覆盖你想到的形状，而 bug 长在你没想到的那个形状上。**
